### 设计思路

三条决定性的设计：
1. 决定一：失败是结果，不是异常
调用方等了十几分钟，需要的是"为什么没成"，不是一个 ConnectionError。
```
推论（后面会一一撞见）：RenderResult 有 ok / error 字段；render() 里有个 except Exception 带 noqa: BLE001；排队超时返回的是失败结果而不是抛异常；/render 端点失败也回 HTTP 200。推论（后面会一一撞见）：RenderResult 有 ok / error 字段；render() 里有个 except Exception 带 noqa: BLE001；排队超时返回的是失败结果而不是抛异常；/render 端点失败也回 HTTP 200。
```

2. 决定二：判据看磁盘，不看模型
模型会说"我做完了"。只有 exports/ 下真出现 .pptx 才算数。
```
推论：run_until(done=...) 收一个谓词而不是解析模型回复；find_latest_pptx() 是"渲染是否成功"的唯一判据；它被反复调用（所以有 stat 竞态，我们昨天修了）；产物 0 字节也要拦（文件在≠产物有效）。
```

3. 决定三：容器常驻共用，不是一任务一个
ocppt-shared 一直活着，每个任务在里面开一个会话，各绑 /workspace/<任务名>。
```
推论（这条最重要，也最容易出事）：
- 容器不再是任务之间的边界 → 隔离全靠按会话下发的两条 permission 规则
- 容器活着但配置可能过期 → 于是有 is_running() 里那三重比对（镜像 ID / 挂载源 / 环境变量）
- 会话必须绑对目录，而绑错不会报错 → 于是 create_session 有三道校验
- 任务名必须唯一 → 昨天加的同名并发防护
- 那个无鉴权的 opencode 服务从"活十几分钟"变成"一直活着" → 于是 --hostname 要收紧到 127.0.0.1
```

回答纠正：
问题1：
这台机器上真正会「在跑」的东西只有两种:
进程 (process)   ← ps / ss 能看到
容器 (container) ← docker ps 能看到

如何寻找可能运行的进程：
按进程找 —— 工具是 ps 或 pgrep。
按端口找 —— 工具是 ss 或 lsof。

进程名不唯一，agent 和 worker 都是 python/uvicorn，ps 出来一堆你分不清谁是谁。
但端口是唯一的,而且端口就是这个服务对外的全部契约。查端口直接回答了「它能不能被访问到」,查进程只回答「有个进程在」——后者可以为真而前者为假(进程活着但没监听成功)。


问题3：
「如果我判断对了,docker ps 的输出里不会有 ocppt-opencode 这个名字。」

排错里的通用解法叫阳性对照:
▎ 先拿这条命令去找一个你 100% 确定存在的东西。
▎ 找得到 → 命令是好的,那么「没找到」就是真的没有。
▎ 找不到 → 问题在命令上,跟服务没关系。
没做对照的阴性结果，不算结果。 这条你之后每次排错都用得上——「日志里没报错」「grep 不到」「接口没被调用」,全都需要先自证工具有效。

ss = socket statistics。取代老的 netstat。它只回答一个问题:
```
这台机器上,谁排错时它的位置
ps      → 「进程活着吗」
ss      → 「服务真的能被连上吗」   ← 这两个可以一真一假
curl    → 「连上之后它答不答」
```

够用线：记住一条命令 + 四个字母

```bash
ss -ltnp
```

| 参数  | 作用      | 类别         |
| --- | ------- | ---------- |
| -l  | 只看监听中的  | 主语(决定看哪一堆) |
| -t  | 只看 TCP  | 过滤         |
| -n  | 不翻译成服务名 | 显示         |
| -p  | 显示是哪个进程 | 显示(需 sudo) |

这一条覆盖你 90% 的场景。 再加上「0.0.0.0 vs 127.0.0.1」这个区别,就到 98% 了。
0.0.0.0 和 127.0.0.1 是完全不同的两件事:

| 绑定地址      | 含义     | 别的机器是否可以连接 |
| --------- | ------ | ---------- |
| 0.0.0.0   | 所有网卡   | 能          |
| 127.0.0.1 | 只有本机回环 | 不能         |
