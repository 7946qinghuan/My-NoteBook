# Docker 零基础入门笔记

> **本笔记的定位**：面向完全没接触过容器、甚至对服务器/端口/进程都不太熟悉的人。 全篇用一套贯穿始终的比喻——**游戏光盘与游戏机**——把 Docker 的抽象概念翻译成生活经验， 同时保证每一条命令、每一个术语在真实工程中都是准确、可直接使用的。

### 比喻设定总表（贯穿全文）

|现实比喻|Docker 概念|一句话解释|
|---|---|---|
|🎮 **游戏光盘**|**镜像 (Image)**|只读的、静态的模板。可以无限次复制使用，本身永远不会被改动|
|📺 **游戏机**|**容器 (Container)**|光盘跑起来之后的那个"运行中的实体"。有开机/关机状态，会产生临时数据|
|🏪 **游戏商店**|**镜像仓库 (Registry)**|存放光盘的地方，最著名的是 Docker Hub|
|🏷️ **光盘上的版本号**|**标签 (Tag)**|同一款游戏的不同版本，如"初版 / 年度版 / 汉化版"|
|💾 **官方记忆卡**|**具名卷 (Named Volume)**|Docker 统一保管的存档介质，你不需要关心它具体放在哪|
|🔌 **你自己的 U 盘**|**绑定挂载 (Bind Mount)**|你亲手指定桌上某个文件夹直接插进游戏机|
|🪛 **生产配方说明书**|**Dockerfile**|一份纯文本的"这张光盘该怎么造"的步骤清单|
|🏭 **压盘工厂**|**docker build**|读配方，自动造出一张新光盘|
|🌐 **局域网交换机**|**网络 (Network)**|让几台游戏机能互相联机说话|
|📋 **多机联机配置总表**|**Docker Compose**|一张表描述"这局需要几台机器、各插什么盘、怎么连线"|
|🛋️ **你的客厅/桌子**|**宿主机 (Host)**|真实世界，也就是你自己的电脑或服务器|

## 术语急救包（看不懂时回来查）

零基础读者常被这几个词卡住，先在这里一次性说清：

- **宿主机 (Host)**：你自己那台真实的电脑（或云服务器）。Docker 装在它上面，所有容器都跑在它里面。比喻里的"客厅 / 桌子"。
- **进程 (Process)**：操作系统里"一个正在运行的程序"。你打开浏览器就是启动了一个进程，关掉就是进程结束。
- **端口 (Port)**：一台电脑上可以同时跑很多网络服务，端口就是**门牌号**，用来区分请求该送给哪个服务。网页服务默认走 80，MySQL 默认走 3306。
- **终端 / 命令行 (Terminal / Shell)**：一个用打字代替点击的黑框框。macOS 叫"终端"，Windows 推荐用 PowerShell 或 WSL。本文所有 `docker ...` 都在这里敲。
- **守护进程 (Daemon)**：在后台默默常驻运行、不显示界面的程序。Docker 的核心 `dockerd` 就是这样一个东西；你敲的 `docker` 命令只是"遥控器"，真正干活的是它。
- **镜像 vs 容器一句话辨析**：**镜像是"类"，容器是"实例"**；或者说镜像是菜谱，容器是照着菜谱炒出来的那盘菜。一份菜谱可以炒 100 盘菜。

# 第零章：为什么需要 Docker？

> 学工具之前先搞懂它解决什么问题，否则后面每条命令都像在背咒语。

## 0.1 那个折磨了程序员二十年的问题

场景：你写好一个网站，在自己电脑上跑得好好的。发给同事，他一运行——报错。发到服务器上——又是另一种报错。

原因是软件从来不是"孤零零一个文件"，它依赖一大堆东西：

- 特定版本的运行时（Python 3.13？还是 3.9？）
- 几十个第三方库，且库和库之间还有版本要求
- 操作系统层面的组件（某个 C 语言的加密库、某个字体、某个时区文件）
- 一堆环境变量和配置文件

只要其中一项和你机器上不一样，程序就可能崩。这就是那句著名的甩锅名言：

> "在我电脑上明明是好的。"（_It works on my machine._）

**Docker 的核心思想**：既然环境这么难复制，那就干脆**把程序连同它需要的整个环境一起打包成一个不可变的整体**，走到哪儿跑到哪儿。

🎮 **游戏机比喻**： 以前发游戏，是把"游戏代码"给你，然后附一张说明书：请先自行安装 DirectX 11、显卡驱动 452 以上、.NET 运行库、还有某个补丁包……你少装一样就黑屏。 Docker 的做法是：把游戏和它需要的全部运行环境**一起压进一张光盘**。任何一台游戏机插上这张盘，画面表现都一模一样。

## 0.2 容器 ≠ 虚拟机（这是新手最大的认知偏差）

很多人第一反应是"这不就是虚拟机吗"。不是，而且差别很关键。

| 对比项          | 虚拟机 (VM)                 | 容器 (Container)                         |
| ------------ | ------------------------ | -------------------------------------- |
| **打包了什么**    | 一整套完整的操作系统 + 虚拟硬件 + 你的程序 | 只有你的程序 + 它依赖的那些库文件                     |
| **内核**       | 每台虚拟机跑自己独立的操作系统内核        | **所有容器共用宿主机的同一个内核**                    |
| **体积**       | 通常几 GB 到几十 GB            | 通常几十 MB 到几百 MB                         |
| **启动速度**     | 几十秒到几分钟（要完整开机）           | **通常一秒以内**（本质只是启动一个进程）                 |
| **一台机器能跑几个** | 个位数到十几个                  | 几十上百个                                  |
| **隔离强度**     | 强（硬件级隔离）                 | 较弱（内核级隔离，靠 Linux 的 namespace 和 cgroup） |

🎮 **游戏机比喻**：

- **虚拟机** = 你在客厅里又摆了**一整台完整的实体游戏主机**：独立电源、独立主板、独立散热、独立系统盘。彻底隔离，但又贵又占地方，开机还慢。
- **容器** = 一台主机上插了很多个**独立的游戏卡槽**。每个卡槽有自己独立的存档区和显示画面，互不干扰，但**大家共用同一块主板和 CPU**。所以便宜、轻、开机快。

**这条比喻推出的重要结论**：既然共用宿主机内核，那么**Linux 容器只能跑在 Linux 内核上**。 所以 Windows 和 macOS 上的 Docker，实际上是先偷偷起了一台极轻量的 Linux 虚拟机，容器跑在里面。这解释了后面很多"为什么 Mac 上挂载文件特别慢""为什么 Windows 上路径要写成那样"的怪现象。

## 0.3 Docker 的三大件

理解这三个词，Docker 就理解了一半：

```
        docker pull                  docker run
镜像仓库 ──────────────▶  本地镜像  ──────────────▶  容器
(Registry)              (Image)                  (Container)
  🏪 游戏商店            🎮 光盘柜里的光盘          📺 正在运行的游戏机
                            ▲
                            │ docker build
                            │
                        Dockerfile
                        🪛 生产配方说明书
```

这张图就是整个 Docker 日常工作流。后面所有章节，都是在给这张图的某一段加细节。

# 第 0.5 章：安装与你的第一条命令

## 0.5.1 该装哪个？

| 你的系统                                  | 装什么            | 说明                                                    |
| ------------------------------------- | -------------- | ----------------------------------------------------- |
| **Windows 10/11**                     | Docker Desktop | 需要先启用 WSL 2（Windows Subsystem for Linux）。安装向导通常会引导你完成 |
| **macOS**（Intel / Apple 芯片都可以）        | Docker Desktop | 注意下载对应芯片的版本                                           |
| **Linux**（Ubuntu / Debian / CentOS 等） | Docker Engine  | 服务器上装这个就够了，不需要图形界面                                    |

> ⚠️ **授权提醒（工程师必须知道）** **Docker Engine 本身是开源免费的**（Apache 2.0）。但 **Docker Desktop** 这个带图形界面的桌面产品有商业授权限制： 个人、教育、非商业开源项目，以及**员工少于 250 人且年营收低于 1000 万美元**的小企业可以免费使用； 超过这个门槛的公司用于商业用途需要付费订阅。 在公司电脑上安装前，请先确认这一点。Linux 服务器上直接装 Docker Engine 不受此限制。

## 0.5.2 验证安装

打开终端，敲三条命令：

```bash
# 1. 看客户端和服务端版本（能同时看到 Client 和 Server 才算真的装好了）
docker version

# 2. 看整体运行状态（有几个容器、几个镜像、用的什么存储驱动）
docker info

# 3. 官方的 "Hello World"，会自动去仓库下载一个极小的测试镜像并运行
docker run hello-world
```

如果第 3 条打印出一段以 `Hello from Docker!` 开头的英文，恭喜，环境没问题。

🎮 **刚才发生了什么**：Docker 发现你本地光盘柜里没有 `hello-world` 这张盘 → 自动去游戏商店（Docker Hub）买了一张 → 塞进一台新游戏机开机 → 游戏播了一段欢迎动画就结束了 → 游戏机自动关机。 这一条命令，就把"拉取镜像 → 创建容器 → 运行 → 退出"的完整生命周期走了一遍。

## 0.5.3 强烈建议先做的一件事：配置镜像加速

Docker Hub 服务器在境外，中国大陆直接拉取常常龟速甚至超时。**这是新手最容易在第一步就放弃的地方**，务必先配好。

Docker Desktop：`Settings` → `Docker Engine`，在 JSON 里加一行 `registry-mirrors`。 Linux：编辑 `/etc/docker/daemon.json`（不存在就新建）：

```json
{
  "registry-mirrors": [
    "https://你的加速器地址"
  ]
}
```

改完重启 Docker：

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
docker info | grep -A 3 "Registry Mirrors"   # 验证是否生效
```

> 💡 可用的加速器地址会随时间变化（很多公共镜像站陆续关停），建议使用你所在云厂商提供的容器镜像服务加速地址，或公司内部的私有仓库。 另外注意：Docker Hub 免费账号对镜像**拉取次数有速率限制**，频繁拉取可能收到 `toomanyrequests` 错误，登录账号（`docker login`）可提高额度。

🎮 **比喻**：默认的游戏商店总部在海外，海运慢还容易丢件。配置加速器 = 改成从本地代理仓库发货。

# 第一章：核心概念与常用命令速查

## 1.1 镜像、容器、仓库的三角关系

先把三者的关系彻底钉死，后面就不会乱：

- **镜像 (Image)** 是**只读**的。你无论怎么折腾容器，都不会改到镜像本身。 就像光盘：你在游戏里怎么造反，光盘上的数据一个字节都不会变。
- **容器 (Container)** = 镜像 + 一个**可写层**。你在容器里新建、修改、删除的文件，全都写在这个薄薄的可写层里。 就像游戏机内置硬盘上的存档区：光盘只读，你的进度写在机器里。
- **仓库 (Registry)** 是镜像的存放和分发中心。公共的叫 Docker Hub，公司内部一般会自建（Harbor、云厂商的容器镜像服务等）。 就是游戏商店。

**一个镜像可以创建出无数个容器，它们之间互不影响。** 一张《塞尔达》光盘可以插进 100 台游戏机，100 个玩家各玩各的存档。

## 1.2 镜像名的完整格式（新手必踩坑）

你在教程里看到的 `nginx`，其实是简写。完整格式是：

```plain text
[仓库地址]/[命名空间]/[镜像名]:[标签]

registry.example.com/myteam/webapp:1.4.2
└──── 仓库地址 ────┘ └命名空间┘ └镜像名┘ └标签┘
```

省略仓库地址时默认是 Docker Hub，省略命名空间时默认是官方镜像库。所以：

|你写的|实际含义|
|---|---|
|`nginx`|`docker.io/library/nginx:latest`|
|`nginx:1.27`|Docker Hub 官方 nginx，标签 1.27|
|`bitnami/nginx`|Docker Hub 上 bitnami 这个组织发布的 nginx|

### ⚠️ 关于 `latest` 的重大误解

`latest` **不是"永远最新"的意思，它只是一个普通的、名字恰好叫 latest 的标签**。 它指向哪个版本完全由镜像发布者决定，而且**会在不同时间指向不同版本**。

这会导致一个经典事故：你今天 `docker run mysql` 一切正常，三个月后同样的命令在新服务器上跑，拉到的是一个大版本更新后的 MySQL，配置不兼容，直接崩。

> 🔒 **工程规范：生产环境永远显式指定版本标签，永远不要用 `latest`。** 写 `mysql:8.4`，不要写 `mysql`。

🎮 **比喻**：`latest` 不是"最新款"，而是货架上贴着"当季主推"标签的那个格子。今年放的是《塞尔达：荒野之息》，明年就换成《王国之泪》了。你说"给我拿主推那张"，拿到什么全看运气。

## 1.3 常用命令速查表

| Docker 命令                    | 概念       | 命令作用说明                     | 游戏机与光盘比喻                       |
| ---------------------------- | -------- | -------------------------- | ------------------------------ |
| `docker images`              | 镜像库      | 查看本地已下载或构建的所有镜像列表          | **光盘柜**：查看柜子里收集的所有游戏光盘         |
| `docker pull <镜像名>:<标签>`     | 拉取镜像     | 从远程仓库下载所需的镜像到本地            | **买光盘**：从游戏商店买一张指定版本的光盘放入柜子    |
| `docker ps`                  | 运行中的容器   | 列出当前正处于运行状态的容器             | **通电开机中的游戏机**：插着光盘且正在玩的机器      |
| `docker ps -a`               | 全部容器     | 列出所有已创建的容器（含运行中与已停止）       | **所有摆出来的游戏机**：包含正在玩的和玩完关机停在一旁的 |
| `docker run <镜像名>`           | 创建并启动容器  | 基于指定镜像**新建**并运行一个容器实例      | **开新机**：搬来一台全新游戏机，插入光盘并开机      |
| `docker stop <容器>`           | 停止容器     | 优雅关闭正在运行的容器                | **正常关机**：先提示保存，再切断电源（光盘仍在机器里）  |
| `docker start <容器>`          | 启动已停止的容器 | 重新启动先前已停止的**同一个**容器        | **按开机键**：给刚才关掉的那台机器重新通电        |
| `docker restart <容器>`        | 重启容器     | 等价于 stop 后再 start          | **按 Reset 键**                  |
| `docker exec -it <容器> bash`  | 进入容器内部   | 在运行中的容器里执行命令 / 进入交互终端      | **拿起手柄操作**：坐到游戏机前操作菜单          |
| `docker logs -f <容器>`        | 查看日志     | 输出容器主进程打印的内容（排错第一命令）       | **看屏幕输出**：盯着游戏机的画面和报错提示        |
| `docker rm <容器>`             | 删除容器     | 彻底清除已停止的容器及其可写层数据          | **拆机回收**：把游戏机拆走（光盘仍在柜子里）       |
| `docker rmi <镜像>`            | 删除镜像     | 从本地抹除指定镜像                  | **扔掉光盘**：把这张盘从柜子里丢掉            |
| `docker inspect <容器/镜像>`     | 查看详情     | 输出完整的 JSON 配置（IP、挂载、环境变量等） | **拆开外壳查线路图**                   |
| `docker cp <容器>:<路径> <本地路径>` | 拷贝文件     | 在宿主机与容器之间传文件               | **用数据线从游戏机里导出截图**              |

### 三条帮你少打无数字的小技巧

1. **容器 ID 可以只打前几位**：`docker stop a1b2c3d4e5f6` 通常写 `docker stop a1b2` 就行，只要在当前所有容器里不重复。
2. **强烈建议永远加 `--name`**：`docker run --name my-nginx nginx`。之后所有命令都能用这个好记的名字代替一串乱码 ID。
3. **临时试验加 `--rm`**：`docker run --rm alpine echo hi`，容器一退出就自动删除，不会在 `docker ps -a` 里留下一堆垃圾。

## 1.4 核心逻辑速记

1. **镜像 (Image)** 是静态的**光盘**，只读，可以重复使用无数次。
2. **容器 (Container)** 是动态的**游戏机**，包含运行时数据（可写层）。
3. **`docker run`** = 拿光盘 + **搬来一台新机器** + 开机 → **每执行一次就多一台机器**。
4. **`docker start` / `docker stop`** = 对**已有的那台机器**开机/关机 → **不会增加新机器**。

> 🚧 **头号新手坑**：很多人调试时反复敲 `docker run`，然后疑惑"为什么端口被占用了"。 因为你已经搬了 5 台游戏机出来，每台都想抢同一个插座。 正确做法是 `docker ps -a` 看一眼，`docker rm` 清掉旧的，或者一开始就用 `--rm`。

## 1.5 容器的状态机

```
                docker run
    [镜像] ──────────────────▶ ┌──────────┐
                               │ Running  │ ◀────────┐
                               │  (Up)    │          │
                               └────┬─────┘          │
                          docker stop│               │ docker start
                          主进程退出  │               │
                                     ▼               │
                               ┌──────────┐          │
                               │  Exited  │ ─────────┘
                               └────┬─────┘
                          docker rm │
                                    ▼
                                 [消失]
```

- `docker ps` 只显示 **Running** 状态的容器。
- `docker ps -a` 显示 **Running + Exited** 全部。
- 容器一旦 `rm`，它的**可写层数据就永久丢失**了（这正是下一章要解决的问题）。

## 1.6 ⚠️ 停止 ≠ 删除（新手第一天必踩）

`docker stop` 和 `docker rm` 是**两件完全不同的事**，但因为口语里都叫"关掉它"，几乎所有人第一天都会搞混。

|-|`docker stop <容器>`|`docker rm <容器>`|
|---|---|---|
|**做了什么**|让容器里的主进程停下来|把容器这个"实体"从系统里彻底抹掉|
|**之后的状态**|`Exited`，仍然存在|不存在了|
|**`docker ps -a` 还看得到吗**|✅ 看得到|❌ 看不到|
|**还占着容器名吗**|✅ **占着**|❌ 释放了|
|**还占着宿主机端口吗**|❌ 释放了|❌ 释放了|
|**还占着磁盘吗**|✅ 可写层还在|❌ 可写层被回收|
|**能恢复吗**|✅ `docker start` 原样复活，数据都在|❌ 可写层数据永久消失|

🎮 **比喻**：

- **`stop` = 按关机键**。游戏机还摆在桌上，光盘还插着，机器内置硬盘里的存档一个字节没少。你随时按开机键（`docker start`）就能接着玩。
- **`rm` = 把游戏机拆了拿去回收**。桌上再也没有这台机器了，机器内置硬盘里的存档也跟着进了粉碎机。**但光盘（镜像）还好好地待在光盘柜里**，你随时能拿它 `docker run` 装一台**全新的**机器——只是新机器是全新出厂状态，之前的进度没了。

### 这个区别会怎么咬到你

**症状一：`The container name "/my-app" is already in use`**

你 `docker stop my-app` 之后想重新 `docker run --name my-app ...`，结果报这个错。

原因：`stop` 只是关机，那台机器还占着 `my-app` 这个名字。解决办法二选一：

```bash
docker start my-app          # 想要原来那台机器和它的数据 → 直接开机
# 或
docker rm my-app             # 想要全新的一台 → 先拆掉旧的，再 run
```

**症状二：`docker ps` 里干干净净，磁盘却越来越满**

因为 `docker ps` 只看运行中的。你几十次调试留下的 `Exited` 容器全都还在，每个都占着磁盘。

```bash
docker ps -a                        # 真相在这里
docker container prune              # 一键清掉所有已停止的容器
```

### 三个实用的组合技

```bash
docker rm -f <容器>        # -f = 先强行停再删，一步到位（最常用）
docker run --rm ...        # 容器一退出就自动删除，调试时不留垃圾（强烈推荐）
docker container prune     # 批量清理所有 Exited 的容器
```

> 💡 **给新手的建议**：临时试验一律加 `--rm`，需要长期跑的服务才起有名字的容器。 这样你的 `docker ps -a` 永远是干净的，不会积累出几十台"关了机但没拆走"的僵尸游戏机。

### 完整的"删除层级"

搞混 stop / rm 的人，通常也会搞混 `rm` 和 `rmi`。一张表看清：

|命令|删的是什么|🎮 比喻|
|---|---|---|
|`docker stop`|什么都不删，只是关机|按关机键|
|`docker rm`|删**容器**（可写层数据一起没）|拆走游戏机|
|`docker rmi`|删**镜像**|扔掉光盘|
|`docker volume rm`|删**数据卷**（持久化数据一起没）|销毁记忆卡 ⚠️|

**注意这三层是独立的**：删了容器，镜像还在、卷也还在。这正是"容器随时可以重建，数据不会丢"的底层保障。

# 第二章：数据卷（Volume）与数据持久化

## 2.1 为什么需要数据卷？

### 2.1.1 问题：不做任何处理会发生什么？

假设你在游戏机里玩《塞尔达传说》，存档打到了终点。如果你把这台游戏机彻底拆除（`docker rm`），**游戏机内部硬盘里的存档数据就全没了**。下次插入同一张光盘启动一台新游戏机（`docker run`），又得从零开荒。

技术上讲：容器的可写层是**跟着容器生死的**。容器删除，可写层一起删除。

这在真实项目里意味着：

- 你的 MySQL 容器删了 → 数据库里所有数据没了
- 你的应用容器重建了 → 用户上传的图片全丢了
- 你更新了镜像版本重新 `run` → 之前的日志一片空白

### 2.1.2 解决方案：把数据放到容器外面去

数据卷的本质思路只有一句话：**让重要数据不要待在容器的可写层里，而是待在容器外面，容器只是"挂载"过来用**。

🎮 **比喻**：给游戏机插一张**外置记忆卡**。所有存档实时写进记忆卡，而不是写进机器内置硬盘。这样：

1. **数据持久化（存档保全）** 即使这台游戏机坏掉、报废、被你砸了（`docker rm`），**记忆卡里的存档依然完好躺在桌上**。
    
2. **数据共享（换机器读同一份存档）** 你换了一台配置更高的新游戏机（升级镜像 / 启动新容器），把记忆卡插上就能接着玩。 甚至可以让多台游戏机挂同一张卡，同时读写共享数据。
    
3. **性能更好** 容器可写层是通过"联合文件系统"叠出来的，写入有额外开销；挂载出去的数据是直接落在宿主机文件系统上的。

## 2.2 ⚠️ 关键辨析：具名数据卷 vs 绑定挂载

**这是全篇最容易被混淆、也最容易被教程一笔带过的地方。** 很多人把两者统称"数据卷"，但它们行为差别很大。

两者都用 `-v` 参数，格式看起来一模一样，**区别只在冒号左边写的是"名字"还是"路径"**：

```bash
# ① 具名数据卷 (Named Volume)：左边是一个「名字」，由 Docker 管理
docker run -v my-data:/var/lib/mysql mysql:8.4

# ② 绑定挂载 (Bind Mount)：左边是一个「宿主机路径」，由你指定
docker run -v /home/me/mysql-data:/var/lib/mysql mysql:8.4
#           ↑ 以 / 或 ./ 或 ~/ 开头，Docker 就认为是路径
```

| 对比项                 | 具名数据卷 (Named Volume)                                  | 绑定挂载 (Bind Mount)                            |
| ------------------- | ----------------------------------------------------- | -------------------------------------------- |
| **数据实际存在哪**         | Docker 自己管理的目录（Linux 上通常在 `/var/lib/docker/volumes/`） | 你指定的宿主机任意目录                                  |
| **需要事先创建吗**         | 不需要，Docker 自动创建                                       | `-v` 会自动建目录（但会建成空目录，常引发问题）                   |
| **能用 docker 命令管理吗** | 能：`docker volume ls / inspect / rm`                   | 不能，它就是普通文件夹                                  |
| **跨机器可移植性**         | 好，配置文件里只写个名字                                          | 差，路径在别人机器上可能不存在                              |
| **首次挂载时的行为**        | 若卷是空的，会**把镜像里该目录的原有内容复制进卷**                           | **直接覆盖**，镜像里原有内容被完全遮住                        |
| **典型用途**            | 数据库数据、生产环境持久化                                         | 本地开发时挂源代码、挂配置文件                              |
| **权限问题**            | 少                                                     | 多（宿主机文件属主 UID 和容器内用户对不上，报 Permission denied） |

🎮 **比喻**：

- **具名数据卷 = 官方原厂记忆卡**。你只需要说"给我插上那张叫 `db_data` 的卡"，卡放在游戏公司统一保管的保险柜里，你不需要知道具体位置。换台机器换个房间都能找到。
- **绑定挂载 = 你自己的 U 盘**。你必须明确说"插我书桌左边第二个抽屉里那个 U 盘"。灵活，但换个房间这个描述就失效了；而且 U 盘一插上，游戏机里原本的存档目录会被**整个盖住**看不见。

> 🔒 **工程规范**：
> 
> - **数据库、生产环境的持久化数据 → 用具名数据卷**
> - **本地开发挂源码实现热重载、挂单个配置文件 → 用绑定挂载**

### 具名数据卷的管理命令

```bash
docker volume ls                    # 列出所有卷（盘点保险柜里有几张记忆卡）
docker volume create my-data        # 手动创建一个卷
docker volume inspect my-data       # 查看卷的详细信息，含它在宿主机上的真实路径
docker volume rm my-data            # 删除卷（数据一起没，谨慎）
docker volume prune                 # 清理所有没被任何容器使用的卷（⚠️ 危险，见 6.4）
```

## 2.3 第三种：`--mount` 写法

Docker 官方文档中提到 `--mount` 比 `-v` 更明确、支持全部可选项，一般更推荐使用。它把参数拆成 `key=value`，可读性更好：

```bash
# -v 的紧凑写法
docker run -v my-data:/app/data nginx

# --mount 的显式写法（等价）
docker run --mount type=volume,src=my-data,dst=/app/data nginx

# 绑定挂载 + 只读
docker run --mount type=bind,src=/home/me/conf,dst=/etc/nginx/conf.d,readonly nginx
```

还有一个重要差异：**`-v` 在宿主机路径不存在时会自动创建一个空目录，而 `--mount` 默认直接报错**。后者其实更安全——如果你路径打错了，`-v` 会静默挂一个空目录上去，导致容器看到的是空的，然后你排查半天想不通。

> 💡 **新手建议**：先把 `-v` 用熟（教程里满地都是），但知道 `--mount` 的存在，写正式项目时优先用它。

## 2.4 只读挂载：一个被低估的好习惯

配置文件挂进容器后，容器**不应该**去改它。加个 `:ro` 让它只读：

```bash
docker run -v /home/me/nginx.conf:/etc/nginx/nginx.conf:ro nginx
```

🎮 **比喻**：给 U 盘拨上"写保护"开关。游戏能读地图，但改不了你桌上的原始文件。

# 第三章：镜像构建 —— `docker commit` 与 `Dockerfile`

场景设定：初始光盘是原版《塞尔达传说》，但你想要一张 **《带自定义 DLC、中文汉化补丁和满级初始存档》的专属定制光盘** 。有两条路可以走。

## 3.1 先理解镜像分层（理解了这个，后面全都通了）

镜像**不是一个大文件，而是一叠只读的"层"（Layer）**。Dockerfile 里每一条会改变文件系统的指令，都会生成新的一层，层层叠加。

```plain text
┌───────────────────────────────────────┐
│        容器可写层(临时读写层)           │
│  容器运行时新增/修改文件；容器销毁便丢失 |
├───────────────────────────────────────┤
│            ↑ 容器运行环境              │
├───────────────────────────────────────┤
│  第4层｜ CMD ["python","main.py"]      │  ← 镜像元数据层(启动指令)
├───────────────────────────────────────┤
│  第3层｜ COPY . /app                  │   ← 业务代码层(只读)
├───────────────────────────────────────┤
│  第2层｜ RUN pip install -r req.txt   │   ← 项目依赖层(只读)
├───────────────────────────────────────┤
│  第1层｜ WORKDIR /app                 │   ← 工作目录环境层(只读)
├───────────────────────────────────────┤
│  第0层｜ FROM python:3.13‑slim        │   ← 基础系统镜像层(只读)
└──────────────────────────────────────┘
                  ↓
     所有镜像层 = 堆叠的只读文件系统
```

🎮 **比喻**：光盘不是一次性烧成的，而是像千层饼一样**一层一层压上去的母版**。底层是原厂系统层，上面压一层汉化补丁，再压一层 MOD，最后压一层你的自定义存档。

分层机制带来三个极其重要的后果，**每一个都会在实战中咬你**：

1. **共享与复用** 十个镜像都 `FROM python:3.13-slim`，宿主机上这个底层**只存一份**。所以你 `docker images` 看到十个镜像各 200MB，实际磁盘占用远小于 2GB。 🎮 十张 MOD 光盘共用同一张原厂母版，工厂只需压一次。
    
2. **构建缓存（Build Cache）** 重新构建时，Docker 从上到下逐条比对：只要这一条指令和它的输入没变，就直接复用上次的层，秒过。**一旦某一层变了，它下面所有层的缓存全部作废，必须重建。** 🎮 说明书第 3 步改了，那第 3 步之后的所有工序都得重新走一遍；但第 1、2 步的半成品可以直接从仓库里拿。
    
3. **删除文件并不能让镜像变小** ⚠️ 如果你在第 3 层下载了一个 500MB 的文件，在第 5 层 `rm` 掉它——**镜像还是大了 500MB**。因为第 3 层是只读的、永远存在的，第 5 层只是"遮住"了它。 🎮 你在第 5 层母版上贴了张贴纸盖住第 3 层的内容，但第 3 层的物理厚度一点没减。 **正确做法**：下载和删除必须写在**同一条 `RUN` 里**：

```dockerfile
# ❌ 错误：镜像里永远留着那个压缩包
RUN wget https://example.com/big.tar.gz
RUN tar -xzf big.tar.gz
RUN rm big.tar.gz

# ✅ 正确：三步在同一层完成，最终层里没有压缩包
RUN wget https://example.com/big.tar.gz \
	&& tar -xzf big.tar.gz \
	&& rm big.tar.gz
```
 

## 3.2 方案一：`docker commit`（手工修改后"翻刻光盘"）

**原理**：

1. 拿原版光盘，插入游戏机开机（`docker run`）。
2. 亲自拿手柄改设置、装汉化包、改玩家数据（`docker exec` 进容器手动操作）。
3. 把当前这台游戏机的状态**整个打包翻刻**成一张新光盘（`docker commit`）。

```bash
docker run -it --name tmp ubuntu bash
# ... 在容器里手动装了一堆东西 ...
exit
docker commit tmp my-custom-image:1.0
```

- **优点**：简单粗暴、直观，**适合临时保存排错现场**（线上容器出了诡异问题，commit 一份下来慢慢研究）。
- **缺点（致命）**：
    - **黑盒**。别人拿到这张盘，完全不知道你装了什么、改了哪个系统文件，无法审计、无法复现。
    - **无法版本控制**。你没法把它放进 Git 做 diff。
    - **体积容易失控**，还可能把 shell 历史、临时文件、甚至误留的密钥一起打包进去。

> 🔒 **工程规范：`docker commit` 只用于排错取证，绝不用于生产镜像的构建。**

## 3.3 方案二：`Dockerfile`（自动化工厂"配方说明书"）

**原理**：你**不亲自去玩游戏**，而是写一份纯文本的《光盘生产配方说明书》（`Dockerfile`）。按步骤写清每个加工细节，交给压盘工厂（`docker build`），工厂严格照配方压制出标准光盘。

- **优点**：**完全透明、可进 Git 版本控制、可复现、体积可优化、易维护**。工业界标准做法。
- **缺点**：需要学语法；每次改动要重新构建（但有缓存，通常很快）。

### 3.3.1 Dockerfile 指令清单

|指令|概念|作用说明|游戏机与光盘比喻|
|---|---|---|---|
|**`FROM`**|基础镜像|指定构建起点，**必须是第一条指令**|**挑选基础母版**：选一张官方原版系统光盘作为改版基础|
|**`WORKDIR`**|工作目录|设置后续指令的默认当前目录，不存在会自动创建|**选择安装路径**：指定在哪个分区/文件夹下进行后续安装|
|**`COPY`**|复制文件|把构建上下文里的文件复制进镜像|**往光盘里放本地文件**：把你写好的代码放入光盘|
|**`ADD`**|复制文件（增强）|同 COPY，但额外支持自动解压 tar、下载 URL|**带自动解压功能的放料口**（能力越大越容易出意外）|
|**`RUN`**|构建时执行|在**构建过程中**执行命令，结果固化成一层|**产线上的加工工序**：压盘前先把 MOD 装好|
|**`ENV`**|环境变量|设置镜像内的环境变量，**运行时也生效**|**出厂预设**：光盘里预置的默认语言、默认难度|
|**`ARG`**|构建参数|只在**构建时**有效的变量，运行时看不到|**产线上的临时参数**：这批盘压 10 张还是 100 张|
|**`EXPOSE`**|声明端口|**仅声明**容器会监听哪个端口（文档作用）|**在外壳上贴标签**："本机 80 号门是网页入口"|
|**`USER`**|运行用户|指定后续指令和容器主进程以哪个用户身份运行|**规定由普通玩家而非管理员操作机器**|
|**`VOLUME`**|声明挂载点|声明某目录应该被挂载（会创建匿名卷）|**标出记忆卡插槽的位置**|
|**`HEALTHCHECK`**|健康检查|定义 Docker 如何判断容器内服务是否真的健康|**自检程序**：定期 ping 一下游戏主程序还活着吗|
|**`ENTRYPOINT`**|固定入口|容器启动时**必定**执行的程序|**开机后必定加载的主程序**|
|**`CMD`**|默认参数/命令|容器启动时的默认命令，或给 ENTRYPOINT 的默认参数|**开机后的默认选项**（可被玩家在开机时覆盖）|

### 3.3.2 ⚠️ `EXPOSE` 的最大误解

**`EXPOSE 8000` 不会打开任何端口，它对外部访问没有任何实际作用。**

它只是写在镜像元数据里的一句"说明文字"，告诉使用者"这个镜像的服务大概监听在 8000"。真正让外部能访问，靠的是运行时的 `-p 8000:8000`。

🎮 **比喻**：`EXPOSE` 是**在游戏机外壳上贴一张标签写"网络接口在这里"**。贴了标签不等于接了网线。要真能联网，必须运行时用 `-p` 拉一条实体线过去。

（唯一的实际功能：`docker run -P`（大写 P）会把所有 `EXPOSE` 的端口随机映射到宿主机高位端口。）

### 3.3.3 ⚠️ `CMD` vs `ENTRYPOINT`（新手第二大坑）

原文这两个常被合并成"默认启动命令"，但它们分工不同，搞混会导致容器启动行为完全不符合预期。

**记忆口诀：`ENTRYPOINT` 是"这台机器是干嘛的"，`CMD` 是"默认参数是什么"。**

||`CMD`|`ENTRYPOINT`|
|---|---|---|
|被 `docker run 镜像 <命令>` 覆盖|**会被完全覆盖**|**不会**，追加的内容变成它的参数|
|如何强行覆盖|直接在 run 后面写命令|必须用 `--entrypoint` 参数|
|定位|默认行为，允许用户替换|固定入口，不允许随便换|

看三个例子就懂了：

```dockerfile
# 例 A：只有 CMD
FROM alpine
CMD ["echo", "hello"]
```

```bash
docker run img              # 输出 hello
docker run img echo bye     # 输出 bye   ← CMD 被整个替换了
```

```dockerfile
# 例 B：只有 ENTRYPOINT
FROM alpine
ENTRYPOINT ["echo"]
```

```bash
docker run img              # 输出空行
docker run img bye          # 输出 bye   ← "bye" 变成了 echo 的参数
```

```dockerfile
# 例 C：两者配合（最佳实践）
FROM alpine
ENTRYPOINT ["ping"]
CMD ["-c", "3", "localhost"]
```

```bash
docker run img              # 执行 ping -c 3 localhost（用默认参数）
docker run img -c 5 8.8.8.8 # 执行 ping -c 5 8.8.8.8（用户换了参数）
```

🎮 **比喻**：`ENTRYPOINT` = 这台街机被**焊死**成了赛车游戏机，它只能跑赛车。`CMD` = 默认选了"新手赛道"，但玩家开机时可以改选别的赛道。

**给新手的实用建议**：如果你只是跑一个 Web 服务，**只写 `CMD` 就够了**，别过早引入 `ENTRYPOINT`。

### 3.3.4 ⚠️ Exec 形式 vs Shell 形式（新手第三大坑）

同一条指令有两种写法，行为不同：

```dockerfile
CMD ["python", "app.py"]     # ✅ Exec 形式（JSON 数组，双引号）
CMD python app.py            # ⚠️ Shell 形式
```

**Shell 形式**会被包装成 `/bin/sh -c "python app.py"`，于是容器里的 **1 号进程是 `sh`，不是你的程序**。 后果：`docker stop` 发出的停止信号（SIGTERM）被 `sh` 收到后**可能不会转发给你的程序**，导致程序没机会保存数据就被强杀，而且要等满 10 秒超时才真正关掉。

> 🔒 **工程规范：`CMD` 和 `ENTRYPOINT` 一律用 Exec 形式（JSON 数组，必须用双引号）。**

🎮 **比喻**：Shell 形式相当于在游戏机和主程序之间多塞了一个"传话中间人"。你按关机键，中间人听见了却不告诉主程序，结果主程序还在傻乎乎地跑，最后被硬断电，存档没了。

### 3.3.5 `.dockerignore`：一个必须养成的习惯

`docker build` 会先把整个"构建上下文"（那个 `.` 目录）打包发给 Docker 引擎。如果你的目录里有 `node_modules`、`.git`、几个 G 的数据文件，**每次构建都要传一遍**，慢得离谱，而且 `COPY . .` 还会把它们一起塞进镜像。

在项目根目录建一个 `.dockerignore`（语法和 `.gitignore` 一样）：

```gitignore
.git
.gitignore
node_modules
__pycache__
*.pyc
.venv
.env
*.log
.DS_Store
README.md
```

> 🔒 **安全提醒**：`.env`、私钥文件**必须**加进 `.dockerignore`。否则 `COPY . .` 会把你的数据库密码永久烧进镜像层里，即使后面 `RUN rm .env` 也删不掉（见 3.1 第 3 条）。

🎮 **比喻**：往光盘里放料之前先过一道筛子，把开发时的草稿纸、垃圾桶、还有写着密码的便利贴全筛掉。

## 3.4 实战配方：一个 Python Web 应用的 Dockerfile

```dockerfile
# ① 挑选基础母版：官方 Python 3.13 精简版（slim 比完整版小很多）
FROM python:3.13-slim

# ② 出厂预设：让 Python 日志实时输出，不缓冲（容器里必加，否则 docker logs 看不到东西）
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

# ③ 选择安装路径
WORKDIR /app

# ④ 先单独复制依赖清单（这一步是缓存优化的关键，见下方讲解）
COPY requirements.txt .

# ⑤ 安装依赖。--no-cache-dir 避免 pip 缓存留在镜像里增大体积
RUN pip install --no-cache-dir -r requirements.txt

# ⑥ 再复制业务代码
COPY . .

# ⑦ 创建一个非 root 用户并切换（安全最佳实践）
RUN useradd --create-home appuser && chown -R appuser:appuser /app
USER appuser

# ⑧ 声明端口（仅文档作用）
EXPOSE 8000

# ⑨ 默认启动命令，Exec 形式
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 逐行讲解 + 游戏光盘类比

|步骤|配方逻辑|🎮 游戏类比|
|---|---|---|
|**① `FROM python:3.13-slim`**|不从零造操作系统，直接用官方做好的 Python 基础镜像。`slim` 是精简变体，体积远小于默认 tag|先买一张原厂《Python 引擎底层驱动光盘》（精简版，去掉了用不上的调试工具）|
|**② `ENV PYTHONUNBUFFERED=1`**|关掉 Python 的输出缓冲，否则日志会卡在缓冲区里，你 `docker logs` 看到一片空白还以为程序死了|把游戏机的"画面输出延迟"关掉，让屏幕实时显示|
|**③ `WORKDIR /app`**|后续所有操作的默认目录|把 `D:\GameApp` 设为默认安装路径|
|**④⑤ 先 COPY 依赖清单再装**|**构建缓存优化的核心**，详见下方|先往光盘里放《MOD 安装清单》，让工厂预装好插件|
|**⑥ `COPY . .`**|把业务代码复制进 `/app`|把你自制的关卡、地图、剧本装入光盘|
|**⑦ `USER appuser`**|容器默认以 root 运行，一旦被攻破风险极大。切换到普通用户|规定这台机器只能用玩家账号操作，不给管理员权限|
|**⑧ `EXPOSE 8000`**|声明服务监听 8000（不产生实际效果，见 3.3.2）|在外壳上贴标签："网页入口在 8000 号门"|
|**⑨ `CMD [...]`**|`docker run` 时自动执行的启动命令|设定按下电源键后的默认行为：不弹菜单，直接跑 Web 服务|

### 🔑 为什么第 ④ 步要单独复制 `requirements.txt`？

这是 Dockerfile 里**最重要的一个优化技巧**，务必理解。

回忆 3.1 讲的缓存规则：**某一层变了，它下面所有层的缓存全部作废**。

- **如果写成 `COPY . .` 然后再 `RUN pip install`**：你每改一行 `app.py`，`COPY . .` 这层就变了 → 下面的 `pip install` 缓存作废 → **每次改一个标点都要重新下载安装全部依赖，等几十秒**。
- **拆开写之后**：只要 `requirements.txt` 没变，`COPY requirements.txt .` 和 `RUN pip install` 两层缓存都命中 → 改代码只重建最后几层 → **构建从几十秒缩短到 1 秒内**。

🎮 **比喻**：把"安装 MOD 插件"（慢、很少变）和"放入关卡文件"（快、天天改）在产线上**分成两道独立工序**。改关卡时，前面装好插件的半成品母版可以直接从仓库拿出来接着用，不用重装插件。

**通用原则：Dockerfile 里，越不容易变的东西写在越上面。**

## 3.5 进阶：多阶段构建（Multi-stage Build）

编译型语言（Go、Java、C++）和前端项目会遇到一个矛盾：**构建需要一大堆工具链（编译器、npm、几百 MB 的 SDK），但运行只需要最终产物。**

如果全塞一个镜像里，最终镜像会有几百 MB 甚至上 G，而且里面带着完整的编译器——既臃肿又是安全隐患。

**多阶段构建**的做法是：用一个"车间镜像"负责编译，再把成品**只拿出来**放进一个干净的"出厂镜像"。

```dockerfile
# ===== 阶段一：车间（带全套工具，体积大，用完就丢）=====
FROM node:22 AS builder
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # 产出静态文件到 /src/dist

# ===== 阶段二：出厂成品（只有一个极小的 nginx）=====
FROM nginx:alpine
COPY --from=builder /src/dist /usr/share/nginx/html
EXPOSE 80
```

最终镜像**只包含第二阶段的内容**——那个 node:22（约 1GB）和所有 npm 依赖全都不在最终产物里。镜像从 1GB+ 降到几十 MB。

🎮 **比喻**：车间里堆满了压盘机、切割机、检测仪（阶段一）。做完之后，**只把压好的那张光盘拿出来装进包装盒发货**（阶段二），整个车间不会跟着盘一起卖给玩家。

## 3.6 构建与运行

```bash
# 构建。-t 打标签，末尾的 . 是构建上下文目录
docker build -t my-custom-app:1.0 .

# 查看构建历史（每一层多大、由哪条指令产生）—— 排查镜像为什么这么大的利器
docker history my-custom-app:1.0

# 运行
docker run -d -p 8000:8000 --name my-app my-custom-app:1.0
```

> 💡 **关于构建输出**：Docker Engine 23.0 起，`docker build` 默认使用 **BuildKit** 构建器。 所以你看到的输出是 `[+] Building 12.3s (10/10) FINISHED` 加上 `=> [2/5] WORKDIR /app` 这样的形式， **而不是老教程里的 `Step 1/7` 和 `Successfully tagged`**。看到新格式说明你的 Docker 是新版，正常现象。 BuildKit 还会并行构建互不依赖的阶段，比旧构建器快很多。

## 3.7 核心对比总结

|特性|`docker commit`|`Dockerfile`|
|---|---|---|
|**比喻**|手工改完再翻刻一张光盘|自动化光盘生产流水线配方|
|**操作方式**|运行容器 → 手动修改 → 导出镜像|编写文本配置 → 自动化 `docker build`|
|**透明度**|**黑盒**（没人知道里面动了什么）|**白盒**（每一步构建指令清晰可见）|
|**可复现性**|无法复现|同一份配方随时随地产出一致结果|
|**维护性**|极差（无法 diff、无法追踪变更）|极佳（可进 Git，可接 CI/CD）|
|**体积控制**|失控|可通过分层、多阶段构建精细优化|
|**适用场景**|临时排错、保存崩溃现场|**一切正式用途**|

# 第四章：核心实战

> 本章每一节都是"**先给命令 → 再拆解现象 → 最后提炼避坑点**"的结构。 建议**边看边敲**，Docker 的东西看十遍不如亲手跑一遍。

## 4.1 实战一：理解容器的生命周期

> **核心铁律：容器的寿命 = 它里面那个主进程（PID 1）的寿命。**
> 
> 🎮 **比喻**：游戏机开机的**唯一目的**就是运行光盘里的主程序。一旦主程序运行完毕退出（通关了、或者只是播了一句台词），游戏机就**立刻自动断电**。

### 4.1.1 🛠️ 亲手验证

```bash
# 1. 启动容器 test1，让它打印 "Hello Docker"
docker run --name test1 alpine echo "Hello Docker"

# 2. 后台启动容器 test2，让它静默休眠 60 秒
docker run -d --name test2 alpine sleep 60

# 3. 查看正在运行的容器
docker ps

# 4. 查看所有容器（包含已退出的）
docker ps -a

# 5. 清理现场
docker rm -f test1 test2
```

### 4.1.2 🔍 现象拆解

|步骤 / 命令|运行现象|背后机制|🎮 比喻|
|---|---|---|---|
|`docker run --name test1 alpine echo "Hello Docker"`|瞬间输出 `Hello Docker`，随后返回命令行|`echo` 是这个容器的主进程。它 0.01 秒就执行完了，**主进程结束 → 容器立刻退出**|**闪退游戏机**：开机 → 播了一句"Hello Docker" → 主程序结束 → 瞬间断电|
|`docker run -d --name test2 alpine sleep 60`|只返回一串容器 ID，不阻塞终端|`sleep 60` 是主进程，要持续 60 秒。**主进程一直在，容器就保持运行**|**定时挂机**：开机 → 跑一个 60 秒倒计时程序 → 保持通电 60 秒|
|`docker ps`|只看到 `test2`（`Up`），**完全看不到 `test1`**|`docker ps` **只扫描运行中的容器**|**看哪台机器电源灯还亮着**|
|`docker ps -a`|两个都在。`test1` 的 STATUS 是 `Exited (0)`|`-a` 列出全部。`(0)` 是**退出码**，0 = 正常结束、无报错|**盘点桌上所有机器**：亮不亮灯都列出来|

### 4.1.3 💡 退出码（Exit Code）—— 排错时的第一条线索

`docker ps -a` 里 `Exited` 后面括号里的数字**不是随便给的**，它是主进程结束时交给操作系统的"结案报告编号"。

#### 第一层：先分清 0 和非 0（这是最重要的判断）

这是 Unix 世界几十年的通用约定，不只 Docker 用：

|退出码|含义|你该怎么想|
|---|---|---|
|**`0`**|主进程**正常干完活，主动退出**|**不是报错。** 是"这活干完了"|
|**非 `0`**|主进程**异常终止**|出事了，去看 `docker logs`|

🎮 **比喻**：`0` 是游戏正常通关后弹出"感谢游玩"然后自动关机；非 `0` 是屏幕闪了一串红色错误码然后断电。

> ⚠️ **`Exited (0)` 不代表一切正常，只代表"没报错地结束了"。** 本节实验里的 `test1` 就是 `Exited (0)`——`echo` 打印完就没事干了，正常退出。 但如果你的 **Web 服务**显示 `Exited (0)`，那反而说明配置错了：一个服务本来就**不该**有"干完活"的时候，它应该永远待命。 🎮 游戏机播完一句台词就"正常关机"，对播报机来说没问题；但你买的是一台该 24 小时开着的服务器，它"正常关机"了就是有问题。

#### 第二层：非 0 时看具体数字

**新手只需要记住加粗的这三个，其余的当查表用就行：**

|退出码|含义|常见原因|
|---|---|---|
|**`1`** ⭐|**程序自身报错退出**|代码抛异常、配置文件缺失、连不上数据库。**最常见，去看日志就对了**|
|`125`|Docker 命令本身有问题|`docker run` 的参数写错了，容器根本没创建成功|
|`126`|命令找到了但执行不了|脚本没有执行权限（忘了 `chmod +x`）|
|**`127`** ⭐|**命令不存在**|拼写错了，或镜像里根本没装那个程序（比如 alpine 里没有 `bash`）|
|**`137`** ⭐|**被强杀（128 + 9 = SIGKILL）**|**绝大多数是内存超限被 OOM Killer 干掉了**，其次是你执行了 `docker kill`|
|`143`|被终止（128 + 15 = SIGTERM）|正常的 `docker stop`，属于预期行为|

> 💡 **为什么是 137 和 143 这种怪数字？** Unix 约定：进程被信号杀死时，退出码 = `128 + 信号编号`。SIGKILL 是 9 号 → 137；SIGTERM 是 15 号 → 143。 知道这条规则，以后见到 `139`（128+11，段错误）之类的也能自己推出来。

🎮 **三个必记码的比喻**： `1` = "游戏运行中崩溃，弹出错误对话框"； `127` = "找不到该光盘，请检查是否插入"； `137` = "机器过热，保护性强制断电"。

#### 怎么把退出码和日志连起来用

退出码告诉你**死法**，日志告诉你**死因**，两个要一起看：

```bash
docker ps -a                                       # ① 看退出码 → 大方向
docker logs --tail 50 <容器>                        # ② 看日志最后几行 → 具体原因
docker inspect -f '{{.State.ExitCode}}' <容器>      # 只想要那个数字时用这条
```

**几乎所有崩溃的真正原因都在 `docker logs` 输出的最后 5~10 行。** 不要从头往下读，直接看结尾。

### 4.1.4 💡 关键总结与避坑

1. **"为什么我的容器一启动就退出？"** —— 全网最高频的 Docker 问题 因为你没给它一个**能持续运行的主进程**。`nginx`、`mysql`、`redis` 这类镜像自带常驻服务所以能一直跑；而 `ubuntu`、`alpine` 这种基础镜像默认执行完一条命令就结束了。
    
    ```bash
    docker run -d ubuntu              # ❌ 立刻退出，因为默认 CMD 是 bash，而 -d 没有终端可交互
    docker run -dit ubuntu            # ✅ -it 分配了伪终端，bash 有地方待着，容器不退
    docker run -d ubuntu sleep 3600   # ✅ 给它一个能跑一小时的主进程
    ```
    
2. **`sleep 60` 结束后会怎样？** 60 秒一过主进程结束，`docker ps` 就看不到它了，它变成 `Exited (0)` 静静躺在 `docker ps -a` 里。
    
3. **不要试图"后台化"你的主程序** 在容器里千万别写 `nginx &` 或者用 systemd 把服务转到后台——那样 PID 1 会立刻结束，容器直接退出。 **容器里的主程序必须在前台运行。** 这也是为什么官方 nginx 镜像的启动命令是 `nginx -g "daemon off;"`。 🎮 **比喻**：你不能让游戏"在后台悄悄跑"，因为游戏机开机的唯一理由就是它。它一躲后台，机器就认为没事干了，直接断电。
    
4. **`docker stop` 不是立刻断电** 它先发一个"请你收拾一下准备关机"的信号（SIGTERM），**默认等 10 秒**，程序还不退才强制断电（SIGKILL）。这就是优雅停机的机会窗口。 `docker kill` 则是直接拔电源，不给任何缓冲。

## 4.2 实战二：部署 Nginx 与端口映射

> **核心铁律：容器的网络环境是隔离的，不做端口映射外部就进不去。**
> 
> 🎮 **比喻**：容器内运行的 Nginx 就像游戏画面里玩家自己开的一间"小书店"（80 号门）。如果不用一条**数据专线**把客厅墙上的插座和游戏里的书店大门接通，客厅里的人（宿主机浏览器）绝对进不去。

### 4.2.1 🛠️ 亲手验证

```bash
# 1. 后台启动并映射端口
docker run -d -p 8080:80 --name my-nginx nginx

# 2. 查看运行状态与端口映射
docker ps

# 3. 验证（浏览器打开 http://localhost:8080，或用命令行）
curl http://localhost:8080

# 4. 看看它的日志（刚才的访问会被记录下来）
docker logs my-nginx

# 5. 清理
docker rm -f my-nginx
```

### 4.2.2 🔍 现象拆解

|步骤 / 命令|运行现象|背后机制|🎮 比喻|
|---|---|---|---|
|`docker run -d -p 8080:80 --name my-nginx nginx`|返回容器 ID。浏览器访问 `http://localhost:8080` 看到 "Welcome to nginx!"|**`-d`**：后台运行，不占用你的终端。<br>**`-p 8080:80`**：把宿主机 8080 端口的流量转发进容器的 80 端口|1. **`-d`**：插上电源丢在客厅默默运行<br>2. **`-p 8080:80`**：拉一条专线，把**客厅墙上 8080 号插座**接到**游戏内书店的 80 号门**|
|`docker ps`|`PORTS` 字段显示 `0.0.0.0:8080->80/tcp`|端口转发规则的可视化：所有发往宿主机 8080 的 TCP 请求都会被送进容器的 80|**查看接线账本**：明确记着"客厅 8080 插座"已绑定到这台机器的"内部 80 门"|
|`curl http://localhost:8080`|打印出 Nginx 的 HTML 源码|请求先到宿主机 8080，经 Docker 网络桥接转发进容器，Nginx 响应|**从客厅敲门进入**：信号沿专线传进游戏里的书店，书店把欢迎页回传|
|`docker logs my-nginx`|看到一行 `"GET / HTTP/1.1" 200` 的访问记录|容器主进程打到标准输出的内容全被 Docker 收集起来|**调出游戏机的运行日志**，看到刚才有人来敲过门|

### 4.2.3 💡 关键总结与常见误区

1. **端口映射格式：`-p 宿主机端口:容器内端口`（顺序千万别写反）**
    
    - **左边（宿主机）**：你在浏览器里输入的那个端口，可以随便改。
    - **右边（容器内）**：服务自己监听的端口，由镜像决定，**不能乱改**（Nginx 是 80，MySQL 是 3306，Redis 是 6379）。
    
    🎮 记忆法：**"从外到内"**，就像写地址从大到小。
    
2. **不加 `-p` 为什么打不开？** Nginx 在容器内正常跑着，但它只在**容器自己的私有网络**里监听 80。宿主机和容器之间没有"专线"，请求根本进不去。
    
3. **完整格式其实是 `-p [宿主机IP:]宿主机端口:容器端口`**
    
    ```bash
    docker run -d -p 8080:80 nginx              # 绑定 0.0.0.0，局域网内任何人都能访问 ⚠️
    docker run -d -p 127.0.0.1:8080:80 nginx    # 只绑定本机，外部访问不到 ✅ 更安全
    ```
    
    > 🔒 **安全提醒**：默认的 `-p 8080:80` 会监听所有网卡。如果这台机器有公网 IP，**你的服务就直接暴露在互联网上了**。 本地开发和内部服务请加 `127.0.0.1:` 前缀。（有大量数据库因为直接 `-p 3306:3306` 暴露公网而被拖库删库。）
    
4. **端口冲突怎么办？** 如果报 `port is already allocated`，说明宿主机 8080 已被占用。要么换个端口（`-p 8081:80`），要么用 `docker ps` 找出占着它的旧容器删掉。
    
5. **`EXPOSE` 和 `-p` 的关系**：见 3.3.2。`EXPOSE` 只是贴标签，`-p` 才是真接线。

## 4.3 实战三：数据持久化（绑定挂载 + 具名卷对照实验）

> **核心铁律：容器是易失的，挂载出去的数据是持久的。**
> 
> 🎮 **比喻**：容器内的文件系统就像游戏机的内置临时存储，机器一拆（`docker rm`）就全没。要保住数据，必须插上外置介质。

### 4.3.1 🛠️ 实验 A：绑定挂载（用你自己的目录）

```bash
# 1. 在宿主机准备一个目录和自定义首页
mkdir -p ~/nginx_data && echo "<h1>Hello Docker! 我的自定义首页</h1>" > ~/nginx_data/index.html

# 2. 启动 Nginx，把这个目录挂到容器的网页根目录
docker run -d -p 8081:80 -v ~/nginx_data:/usr/share/nginx/html --name v-nginx nginx

# 3. 验证
curl http://localhost:8081

# 4. 不重启容器，直接在宿主机改文件
echo "<h1>我改了内容，而且没重启容器</h1>" > ~/nginx_data/index.html
curl http://localhost:8081      # 立刻变了

# 5. 彻底删除容器，检查本地文件是否还在
docker rm -f v-nginx && cat ~/nginx_data/index.html
```

### 4.3.2 🔍 现象拆解

|步骤|运行现象|背后机制|🎮 比喻|
|---|---|---|---|
|`mkdir ~/nginx_data && echo ...`|宿主机上多了一个含自定义 HTML 的目录|在宿主机准备好数据源|**在桌上准备一个 U 盘**，里面存好你自己画的地图|
|`docker run -v ~/nginx_data:/usr/share/nginx/html ...`|容器启动，其内部 `/usr/share/nginx/html` 被宿主机目录**完全覆盖**|建立绑定挂载。容器读那个路径时，实际读的是宿主机的 `~/nginx_data`|**插上 U 盘**：游戏内书店展示的直接就是你 U 盘里的新地图，原厂内容被盖住|
|`curl http://localhost:8081`|输出你的自定义 HTML，不是 Nginx 默认页|Nginx 读取并渲染了挂载进来的文件|**画面刷新**：显示的正是 U 盘里的内容|
|在宿主机改文件后再 curl|**不重启容器，内容立刻变了**|挂载是实时双向的，不是复制|**U 盘里换了张地图，游戏画面立刻跟着变**|
|`docker rm -f v-nginx && cat ...`|容器没了，但 `index.html` 完好无损|删除容器只回收了容器可写层，**挂载的数据独立于容器存在**|**把游戏机砸了，桌上的 U 盘依然完好**，随时能插进下一台新机器|

### 4.3.3 🛠️ 实验 B：具名卷（对照组）

```bash
# 1. 用具名卷启动一个 MySQL（注意冒号左边是「名字」不是路径）
docker run -d --name db-test \
  -e MYSQL_ROOT_PASSWORD=demo_pass \
  -v mysql_data:/var/lib/mysql \
  mysql:8.4

# 2. Docker 自动创建了这个卷
docker volume ls

# 3. 看看它到底存在宿主机的哪里
docker volume inspect mysql_data

# 4. 把容器整个删掉
docker rm -f db-test

# 5. 卷还在！数据一个字节没少
docker volume ls

# 6. 用同一个卷启动一台"新游戏机"，数据完全延续
docker run -d --name db-test-2 \
  -e MYSQL_ROOT_PASSWORD=demo_pass \
  -v mysql_data:/var/lib/mysql \
  mysql:8.4

# 7. 清理（⚠️ 第二条会真的删掉数据）
docker rm -f db-test-2
docker volume rm mysql_data
```

🎮 **比喻**：这次用的是**官方原厂记忆卡**。你只说"给我那张叫 `mysql_data` 的卡"，不用管它放在保险柜哪一格。砸了游戏机，卡还在保险柜里；换台新机器插上，存档完美延续。

### 4.3.4 💡 关键总结与常见坑

1. **`-v` 语法**：`-v 宿主机路径或卷名:容器内绝对路径[:ro]` 容器内路径**必须是绝对路径**。宿主机侧建议也用绝对路径（`$(pwd)/data` 而不是 `./data`，避免歧义）。
    
2. **数据是双向实时同步的** 宿主机改 → 容器立刻看到；容器内改 → 宿主机文件也变。这正是本地开发挂源码实现热重载的原理。
    
3. **⚠️ 挂载会"遮住"镜像里的原有内容** 如果你挂一个**空目录**到 `/usr/share/nginx/html`，Nginx 的默认页面就会消失，访问变成 403/404。很多人在这里困惑半天。 🎮 **比喻**：插上一个空 U 盘，游戏机就只能看到这个空 U 盘，原厂预装的地图被完全遮住了。 （**具名卷是个例外**：首次挂载空卷时，Docker 会先把镜像里该目录的内容复制进卷。这也是具名卷对数据库更友好的原因之一。）
    
4. **⚠️ 权限问题（`Permission denied`）** 绑定挂载会**保留宿主机的文件属主**，这是最容易卡住新手的一类报错。**因为坑比较深，单独放在 4.3.5 讲。**
    
5. **⚠️ macOS / Windows 上绑定挂载会明显变慢** 因为容器实际跑在一台隐藏的 Linux 虚拟机里，宿主机目录要跨虚拟机边界共享。挂 `node_modules` 这类含几万个小文件的目录时尤其明显。 规避方式：把依赖目录用**具名卷**盖住，只挂源码。
    
6. **生产环境的实际价值**
    
    - **数据库持久化**：MySQL 的 `/var/lib/mysql`、PostgreSQL 的 `/var/lib/postgresql/data` 必须挂出来，否则容器重建 = 删库。
    - **用户上传文件**：头像、附件目录必须挂出来。
    - **配置文件注入**：把宿主机写好的 `nginx.conf` 以 `:ro` 挂进去，改配置不需要重建镜像。

### 4.3.5 ⚠️ 容器里默认是 root —— 属主坑与 chown

这一节要解决两个看似矛盾、实则同源的问题：

> **问题 A**：容器里是 root，什么都能干，很危险 → 所以应该切换成普通用户。 **问题 B**：一切换成普通用户，挂载的目录就 `Permission denied` 了 → 于是很多人只好切回 root，或者 `chmod 777`。

### 先理解根源：Linux 只认数字，不认名字

**文件的属主在 Linux 底层记录的是一个数字（UID），不是用户名。**"用户名 ↔ UID"的对应关系写在各自系统的 `/etc/passwd` 里，而**宿主机和容器有各自独立的 `/etc/passwd`**。

于是就出现了这个错位：

```
宿主机                              容器内
├─ 你的用户 ubuntu → UID 1000       ├─ root      → UID 0
└─ ~/data 属主 = UID 1000           └─ appuser   → UID 1000？还是 999？看镜像怎么建的
```

**绑定挂载不会做任何 UID 转换，它原样把文件带进去。** 容器内的内核看到 `~/data` 属主是 `1000`，然后看当前进程的 UID：

- 进程是 **root（UID 0）** → root 无视一切权限 → **能读能写，一切正常** ✅
- 进程是 **appuser（UID 999）** → 999 ≠ 1000，且目录对其他人没有写权限 → **`Permission denied`** ❌

🎮 **比喻**：宿主机和游戏机各自有一本员工名册，但**门禁卡上只印工号，不印名字**。你桌上的 U 盘设成"只有 1000 号工号能写"。游戏机里干活的是 999 号——刷卡，滴，拒绝。而 root 是 0 号，那是**万能钥匙**，任何门都能开。

### 亲手复现这个坑

```bash
# 1. 宿主机建目录，属主是你自己（通常 UID 1000）
mkdir -p ~/perm-test && ls -ldn ~/perm-test     # -n 显示 UID 数字而非用户名

# 2. 默认 root 身份运行 → 写得进去
docker run --rm -v ~/perm-test:/data alpine sh -c "id && touch /data/by-root.txt && echo 写入成功"

# 3. 换成一个不匹配的 UID 运行 → 撞墙
docker run --rm --user 999 -v ~/perm-test:/data alpine sh -c "id && touch /data/by-999.txt"
#   → touch: /data/by-999.txt: Permission denied

# 4. 用你自己的 UID 运行 → 又通了
docker run --rm --user $(id -u):$(id -g) -v ~/perm-test:/data alpine sh -c "id && touch /data/ok.txt && echo 写入成功"

# 5. 回到宿主机看看第 2 步那个文件的属主是谁
ls -ln ~/perm-test
#   → by-root.txt 的属主是 0，也就是 root！你自己的账号可能都删不掉它

# 清理（可能需要 sudo）
sudo rm -rf ~/perm-test
```

第 5 步顺带暴露了**以 root 跑容器的另一个副作用**：容器往挂载目录里写出的文件，**属主是 root**。等你在宿主机上想编辑或删除它们时，会发现自己没权限，还得 `sudo`。CI 流水线里这个问题尤其烦人。

### 四种解法，按推荐度排序

|方案|做法|评价|
|---|---|---|
|**① 运行时对齐 UID**（开发首选）|`docker run --user $(id -u):$(id -g) ...`|✅ 不改镜像、不改宿主机，最省事。缺点是容器里这个 UID 没有对应用户名，提示符会显示 `I have no name!`，不影响功能|
|**② 调整宿主机目录属主**（生产首选）|`sudo chown -R 1000:1000 /srv/appdata`（1000 换成镜像文档里写的那个 UID）|✅ 最干净。官方镜像通常会在文档里注明它以哪个 UID 运行|
|**③ 改用具名卷**|`-v app_data:/data` 代替 `-v ~/data:/data`|✅ 直接绕开问题。具名卷首次创建时 Docker 会把镜像里该目录的属主/权限一并继承过来|
|**④ `chmod -R 777`**|给所有人全部权限|❌ **能跑通，但等于把门锁全拆了**。任何拿到宿主机普通账号的人都能改你的数据。别用|

🎮 **比喻**：①是"给游戏机里的工人换一张 1000 号工号卡"；②是"把 U 盘的门禁改成允许 999 号"；③是"改用官方记忆卡，工号问题公司统一处理好了"；④是"干脆把门拆了，谁都能进"。

### 那到底该不该用非 root 用户？

**该用。** 两个问题不冲突——安全上要切换成非 root，权限上用方案 ①②③ 对齐即可。

Dockerfile 里的标准写法（3.4 节示例用的就是这个）：

```dockerfile
# 创建一个固定 UID 的用户，UID 写死方便宿主机侧对齐
RUN groupadd -g 1000 appuser && \
    useradd -u 1000 -g 1000 --create-home appuser

# ⚠️ 顺序很重要：chown 必须在 USER 之前，因为切换后就没权限改属主了
COPY --chown=appuser:appuser . /app

USER appuser
```

两个细节值得记住：

1. **`COPY --chown=appuser:appuser`** 比先 `COPY` 再 `RUN chown` 更好——后者会**多产生一个完整的镜像层**（复制一份全部文件只为改属主），镜像体积直接翻倍。
2. **`USER` 之后就不能再装软件了**。所有 `apt-get install`、`pip install` 必须写在 `USER` 之前。

> 💡 **排错口诀**：看到 `Permission denied`，第一件事是同时看两个数字—— 宿主机侧 `ls -ldn <目录>` 看属主 UID，容器侧 `docker exec <容器> id` 看进程 UID。 **两个数字对上，问题就没了。**

## 4.4 实战四：环境变量与一键部署 MySQL

> **核心铁律：镜像是通用固化的，环境变量是启动时注入的个性化参数。**
> 
> 🎮 **比喻**：你买了一张通用的《模拟城市》光盘（MySQL 镜像）。每次插盘开机，机器都会弹出**开机初始化设置菜单**（`-e` 参数）。你必须在这时填入管理员密码、城市名字，游戏才能建城。

### 4.4.1 🛠️ 亲手验证

```bash
# 1. 启动 MySQL 容器，注入密码和初始数据库，并把数据挂到具名卷
docker run -d --name my-mysql \
  -p 127.0.0.1:3306:3306 \
  -e MYSQL_ROOT_PASSWORD=secret_password \
  -e MYSQL_DATABASE=app_db \
  -v mysql_data:/var/lib/mysql \
  mysql:8.4

# 2. 确认状态（首次启动要初始化，可能需要等 10~30 秒）
docker ps

# 3. 初始化过程都在日志里，等它出现 "ready for connections"
docker logs -f my-mysql

# 4. 进容器验证（交互式登录，密码在提示后输入，不写在命令行里）
docker exec -it my-mysql mysql -u root -p
# 登录后执行： SHOW DATABASES;   然后 exit;

# 5. 清理
docker rm -f my-mysql && docker volume rm mysql_data
```

### 4.4.2 🔍 现象拆解

|步骤 / 命令|运行现象|背后机制|🎮 比喻|
|---|---|---|---|
|`docker run -e MYSQL_ROOT_PASSWORD=... -e MYSQL_DATABASE=...`|返回容器 ID|**`-e KEY=VALUE`** 把参数注入容器的环境变量。MySQL 镜像的启动脚本会读取它们完成初始化。<br>**`MYSQL_ROOT_PASSWORD` 是必填的**，不传容器会打印错误后直接退出|**开机填初始化菜单**：插盘开机瞬间填入管理员密码和城市名。游戏引擎读到参数后才肯生成新世界|
|`docker ps`|状态从 `Up (health: starting)` 逐渐变成 `Up (healthy)`；PORTS 显示 `127.0.0.1:3306->3306/tcp`|只有必填变量都给对了，MySQL 才能完成表空间和权限初始化并持续监听 3306|**电源灯稳定常亮**，且 3306 号联机插座已接通|
|`docker logs -f my-mysql`|一大段初始化日志，最后出现 `ready for connections`|**数据库首次启动要建系统表，通常十几到几十秒。这段时间内它虽然 `Up` 但还连不上**|**游戏正在生成世界地图**，进度条走完才能进游戏|
|`docker exec -it my-mysql mysql -u root -p`|交互式输入密码后进入 MySQL 命令行，能看到 `app_db`|`docker exec` 在运行中的容器里再起一个进程，调用容器内自带的 mysql 客户端|**拿起手柄**：伸手进游戏机操作，输入开机时设的密码，屏幕列出刚建好的 `app_db` 地图|

### 4.4.3 💡 关键总结与工程实践

1. **为什么数据库镜像离不开环境变量？** 官方通用镜像不可能把密码硬编码在光盘里（那全世界的 MySQL 密码就都一样了）。`-e` 让**同一张光盘**在不修改镜像的前提下，为不同用户初始化出个性化、独立的实例。
    
2. **⚠️ 密码不要写在命令行里** `mysql -u root -psecret` 这种写法，MySQL 自己都会警告 `Using a password on the command line interface can be insecure`。原因是密码会留在你的 shell 历史记录里，在多用户机器上还能被 `ps` 看到。 **改用 `-p` 不带值**，让它交互式提示输入。
    
3. **⚠️ 环境变量并不是"安全"的存密码方式** `docker inspect` 能看到全部环境变量的明文。生产环境请用 Docker Secrets、云厂商的密钥管理服务，或者至少用 `--env-file` 把它们放进一个受权限保护的文件里：
    
    ```bash
    # .env 文件（记得加进 .gitignore 和 .dockerignore！）
    MYSQL_ROOT_PASSWORD=secret_password
    MYSQL_DATABASE=app_db
    ```
    
    ```bash
    docker run -d --name my-mysql --env-file .env -v mysql_data:/var/lib/mysql mysql:8.4
    ```
    
4. **⚠️ 版本选择：不要再用 `mysql:8.0`** MySQL 8.0 已于 **2026 年 4 月随 8.0.46 版本进入 End of Life**，官方明确建议升级到 **MySQL 8.4 LTS** 或更新的 LTS 版本。新项目请直接用 `mysql:8.4`。 （另外注意 Docker Hub 上的 `lts` 标签指向的是当前最新 LTS，会随时间变化，同样不建议在生产里用。）
    
5. **⚠️ 环境变量只在"数据目录为空"时生效** 如果你挂载的卷里已经有数据了，MySQL 启动时会跳过初始化，`MYSQL_ROOT_PASSWORD` 的修改**不会生效**。 这就是"我明明改了密码怎么还是登不上"的原因。要重来必须删掉卷。 🎮 **比喻**：开机菜单只在**第一次建城**时弹出。城已经建好了，你再改开机参数，游戏只会说"读取已有存档"，直接无视你。
    
6. **生产环境的"四件套"黄金组合**
    
    ```bash
    docker run -d \
      --name prod-mysql \
      --restart unless-stopped \                    # ① 宿主机重启后自动拉起
      -p 127.0.0.1:3306:3306 \                      # ② 只监听本机，不暴露公网
      -v mysql_data:/var/lib/mysql \                # ③ 数据持久化到具名卷
      --env-file /etc/myapp/mysql.env \             # ④ 密码从受保护文件读取
      mysql:8.4
    ```
    
7. **`--restart` 重启策略速查**
    
    |策略|行为|🎮 比喻|
    |---|---|---|
    |`no`（默认）|挂了就挂了|断电了就躺着|
    |`on-failure[:次数]`|非 0 退出码才重启，可限次数|只有"异常断电"才自动重开，且最多重开 N 次|
    |`always`|总是重启，**包括你手动 stop 后宿主机重启也会拉起**|只要通电就必然开机，连你主动关的都会被拉起来|
    |`unless-stopped`|总是重启，**但你手动 stop 的会保持关闭**|尊重你的手动关机意图 ✅ 通常首选|

## 4.5 实战五：用 Dockerfile 打包并运行自己的应用

> **核心铁律：Dockerfile 是专属光盘的"自动化加工配方"。**
> 
> 🎮 **比喻**：前面几节我们都在买现成的官方原版光盘（`nginx`、`mysql`）。现在你自己写了一款游戏（业务代码），需要按配方说明书让工厂**亲自压制一张专属光盘**，再插进游戏机运行。

### 4.5.1 🛠️ 从零完成打包与部署

```bash
# 1. 创建项目目录
mkdir -p ~/my-web-app && cd ~/my-web-app

# 2. 写应用代码
cat << 'EOF' > app.py
from flask import Flask
app = Flask(__name__)

@app.route('/')
def hello():
    return "<h1>Hello! 这是从我亲自打包的 Docker 镜像中运行的网页！</h1>"

@app.route('/health')
def health():
    return {"status": "ok"}

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
EOF

# 3. 写依赖清单（生产项目请锁定版本）
cat << 'EOF' > requirements.txt
flask==3.1.3
EOF

# 4. 写 .dockerignore（别忘了这一步）
cat << 'EOF' > .dockerignore
.git
__pycache__
*.pyc
.venv
.env
EOF

# 5. 写 Dockerfile
cat << 'EOF' > Dockerfile
FROM python:3.13-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 5000
CMD ["python", "app.py"]
EOF

# 6. 送入工厂压盘（注意末尾的点，代表构建上下文 = 当前目录）
docker build -t my-custom-app:1.0 .

# 7. 插盘开机并验证
docker run -d -p 5000:5000 --name running-my-app my-custom-app:1.0
curl http://localhost:5000

# 8. 清理
docker rm -f running-my-app
```

> ⚠️ **`host='0.0.0.0'` 是必须的，不能写 `127.0.0.1`。** 因为容器里的 `127.0.0.1` 指的是**容器自己**，不是宿主机。绑定到 `127.0.0.1` 意味着"只接受容器内部的请求"，端口映射进来的外部流量会被拒绝，你会得到一个诡异的"连接被重置"。 🎮 **比喻**：书店老板只在自己房间里开了个小窗口对内营业，你从客厅拉的专线接过去，发现大门根本没开。**容器里的服务必须监听 `0.0.0.0`（所有网卡）。**

### 4.5.2 🔍 现象拆解

|步骤|运行现象|背后机制|🎮 比喻|
|---|---|---|---|
|`cat ... > Dockerfile`|本地多了一份纯文本配方|明确了基础环境、路径、依赖、代码、运行用户和启动命令|**写光盘加工说明书**：选什么底板、装什么 MOD、放什么关卡|
|`docker build -t my-custom-app:1.0 .`|BuildKit 输出 `[+] Building 15.2s (12/12) FINISHED`，中间每层显示 `=> [3/6] COPY requirements.txt .`|Docker 逐条解析 Dockerfile，创建镜像层并缓存，最终打上 `my-custom-app:1.0` 标签|**工厂压盘**：按说明书逐道工序加工，最终印出贴着 `my-custom-app:1.0` 标签的专属光盘|
|**再次执行第 6 步**|大部分层显示 `CACHED`，几乎瞬间完成|命中构建缓存|**半成品母版直接从仓库取用**，不用重走工序|
|**改一行 app.py 后再构建**|前面几层仍 `CACHED`，只有 `COPY . .` 之后的层重建|3.4 节讲的缓存优化生效了|只重压最上面那一层母版|
|`docker run -d -p 5000:5000 ...`|访问 `localhost:5000` 显示自定义页面|用刚造好的镜像启动容器，端口映射通了|**插上自制光盘，接通 5000 号插座，开机**|

### 4.5.3 💡 关键总结

1. **`docker build` 末尾的 `.` 是什么？** 是**构建上下文（Build Context）**。Docker 会把这个目录打包发给构建引擎，供 `COPY` / `ADD` 取用。所以 `COPY ../other/file .` 是**不合法的**——上下文之外的文件拿不到。
    
2. **构建缓存优化**：见 3.4 节。核心是"越不常变的写在越上面"。
    
3. **镜像标签管理**：养成打两个标签的习惯。
    
    ```bash
    docker build -t my-app:1.0.3 -t my-app:latest .
    ```
    
    版本号标签用于精确回滚，`latest` 用于本地方便。**部署时永远引用版本号标签。**
    
4. **查看镜像为什么这么大**：`docker history my-custom-app:1.0`，能看到每一层的体积和产生它的指令。

## 4.6 实战六：容器网络与容器间通信

> 这是原本很多入门教程会跳过、但一旦做多容器项目就必踩的一节。
> 
> **核心铁律：默认网络下容器之间不能用名字互相访问；自建网络才可以。**
> 
> 🎮 **比喻**：客厅里摆了两台游戏机，光是都通着电并不代表它们能联机。得先拉一条局域网线、组一个"联机房间"，它们才能互相喊名字。

### 4.6.1 Docker 的三种常用网络模式

|模式|说明|🎮 比喻|
|---|---|---|
|**bridge**（默认）|每个容器分配一个私有 IP，通过虚拟网桥与宿主机通信|每台游戏机接到同一个路由器上，各有内网 IP|
|**host**|容器直接使用宿主机的网络栈，**不做隔离，也不需要 `-p`**|游戏机直接焊在客厅的网络主干上，没有中间路由|
|**none**|完全没有网络|游戏机彻底断网，单机模式|

### 4.6.2 ⚠️ 默认网桥 vs 自定义网桥（关键差异）

新手常见困惑："我起了两个容器，为什么 A 里 `ping b` 说找不到主机？"

因为它们都在 Docker 的**默认 bridge 网络**上，而**默认 bridge 网络不提供容器名的 DNS 解析**。你只能用 IP 访问，而 IP 每次重启都可能变。

**自定义 bridge 网络才带内置 DNS**，可以直接用容器名当主机名互访。

### 4.6.3 🛠️ 亲手验证

```bash
# —— 对照组：默认网络 ——
docker run -d --name box-a alpine sleep 3600
docker run -d --name box-b alpine sleep 3600
docker exec box-a ping -c 2 box-b        # ❌ 报 bad address 'box-b'
docker rm -f box-a box-b

# —— 实验组：自定义网络 ——
docker network create my-net             # 拉一条局域网线，建个联机房间

docker run -d --name box-a --network my-net alpine sleep 3600
docker run -d --name box-b --network my-net alpine sleep 3600
docker exec box-a ping -c 2 box-b        # ✅ 通了！直接用容器名就能找到对方

# 清理
docker rm -f box-a box-b && docker network rm my-net
```

### 4.6.4 💡 关键总结

1. **多容器项目请务必创建自定义网络**（用 Compose 的话它会自动帮你建，见 4.7）。
    
2. **容器互访用「容器名 + 容器内端口」，不要用宿主机映射端口** 两个容器在同一网络里通信走的是内网，走的是对方的**原始端口**，不经过 `-p` 映射。
    
    ```text
    ✅ 应用连数据库写：  mysql://user:pass@my-mysql:3306/app_db
                                         └─容器名─┘└原始端口┘
    ❌ 不要写：          mysql://user:pass@localhost:3307/app_db
    ```
    
    🎮 **比喻**：两台游戏机在同一个联机房间里，直接喊对方的名字就行，不需要绕到客厅墙上的插座再绕回来。
    
3. **容器里的 `localhost` 指容器自己** 这是极高频的错误来源。容器 A 里写 `localhost:3306` 是在找**容器 A 自己**的 3306，而不是数据库容器。
    
4. **容器想访问宿主机上的服务怎么办？** Docker Desktop（Mac/Windows）上用特殊域名 `host.docker.internal`。Linux 上需要在 `docker run` 时加 `--add-host=host.docker.internal:host-gateway`。
    
5. **常用网络命令**
    
    ```bash
    docker network ls                      # 列出所有网络
    docker network create my-net           # 创建
    docker network inspect my-net          # 看这个网络里有哪些容器、各自 IP 是多少
    docker network connect my-net box-a    # 把已存在的容器接入某网络
    docker network rm my-net               # 删除
    ```

## 4.7 实战七：用 Docker Compose 一键启动"网站 + 数据库"

> **核心铁律：Compose 是多容器协同的"联机作战调度脚本"。**
> 
> 🎮 **比喻**：前面每一节我们都是一台一台手动开机（手敲 `docker run`），还要手动拉网线、插记忆卡、填密码。现在要搞"多人联机"（Web + 数据库），一台台配极易出错。Compose 就是一张**多机联机配置总表**，按一次总开关，系统自动搬机器、插光盘、组网、按顺序通电。

### 4.7.1 🛠️ 三步完成组合部署

```bash
# 1. 创建项目目录
mkdir -p ~/compose-demo && cd ~/compose-demo

# 2. 写密码文件（不进 Git）
cat << 'EOF' > .env
MYSQL_ROOT_PASSWORD=secret_password
MYSQL_DATABASE=my_game_db
EOF
echo ".env" > .gitignore

# 3. 写配置总表
cat << 'EOF' > compose.yaml
services:
  # ===== 服务一：数据库游戏机 =====
  db:
    image: mysql:8.4
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${MYSQL_DATABASE}
    volumes:
      - db_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 40s

  # ===== 服务二：网页游戏机 =====
  web:
    image: nginx:1.27
    restart: unless-stopped
    ports:
      - "127.0.0.1:8082:80"
    depends_on:
      db:
        condition: service_healthy    # ← 关键：等数据库真的健康了才启动

volumes:
  db_data:            # 声明一张由 Compose 统一管理的具名记忆卡
EOF

# 4. 一键联机启动（-d 后台运行）
docker compose up -d

# 5. 看状态和日志
docker compose ps
docker compose logs -f db

# 6. 玩完收台
docker compose down
```

### 4.7.2 🔍 配置逐项拆解

|配置项 / 命令|背后机制|🎮 比喻|
|---|---|---|
|**`services:`**|定义这个项目包含的所有容器（`db` 和 `web`）|**摆开联机台面**：声明这局要用几台游戏机|
|**`image: mysql:8.4`**|指定用哪张光盘的哪个版本。**显式版本号，不用 latest**|指定"《模拟城市》8.4 版光盘"，不是"当季主推那张"|
|**`environment:`**|等价于 `docker run -e`。`${VAR}` 会自动从同目录的 `.env` 文件读取|开机初始化菜单的填写内容，从旁边的便签本上抄|
|**`volumes: - db_data:/var/lib/mysql`**|把具名卷 `db_data` 挂到 MySQL 数据目录|把标着 `db_data` 的专属记忆卡插进数据库游戏机|
|**`healthcheck:`**|定期执行一条命令判断服务是否**真的能用**（不只是进程活着）|**自检程序**：每 10 秒 ping 一下游戏主程序，连续通过才算"世界加载完毕"|
|**`depends_on: db: condition: service_healthy`**|**等 `db` 的 healthcheck 通过后**才创建 `web`|**必须等数据库游戏机的"世界生成"进度条走完**，网页机才能开机|
|**`ports: "127.0.0.1:8082:80"`**|端口映射，且只监听本机|只在客厅内部拉专线，不接到大门外|
|**`restart: unless-stopped`**|宿主机重启后自动拉起，但尊重你的手动 stop|来电自动开机，但你主动关的那台保持关着|
|**`docker compose up -d`**|解析配置 → 拉镜像 → 建网络 → 建卷 → 按依赖顺序启动全部容器|**按下总电源**：自动搬机器、插盘、拉网线、顺序通电|
|**`docker compose down`**|停止并删除本项目的容器和网络（**具名卷默认保留**）|**收台面**：拆掉游戏机和网线，只留下带存档的记忆卡|

### 4.7.3 ⚠️ 关于 `depends_on` 的重大更正

**这是 Compose 里最容易被写错、也最容易被教程误导的一点。**

很多教程（包括本笔记的旧版）写：

```yaml
depends_on:
  - db          # ❌ 短语法
```

并声称"这样会等数据库就绪"。**这是错的。**

Docker 官方文档写得很明确：短语法的 `depends_on` **只保证容器的启动顺序，不保证被依赖的服务已经能处理请求**。MySQL 容器"启动了"和"能接受连接了"之间隔着十几到几十秒的初始化。

后果就是那个经典现象：**第一次 `up` 时 web 崩溃，第二次 `up` 就好了**（因为第二次数据库早就初始化完了）。

**正确做法**是用长语法 + `condition`，配合被依赖服务的 `healthcheck`：

```yaml
depends_on:
  db:
    condition: service_healthy    # 等它 healthcheck 通过
```

`condition` 有三个取值：

|取值|含义|
|---|---|
|`service_started`|默认值，等价于短语法。只等容器启动|
|`service_healthy`|**等 healthcheck 通过**（要求被依赖服务定义了 healthcheck）|
|`service_completed_successfully`|等被依赖服务跑完并以 0 退出（适合数据库迁移这类一次性任务）|

> 💡 **但即使这样，应用层的重连重试逻辑仍然不能省。** 因为运行期间数据库也可能短暂重启，Compose 的启动顺序管不了那时候的事。健壮的应用应该自带带退避的重连机制。

🎮 **比喻**：短语法 `depends_on` 只是"**先按下数据库机的电源键，再按网页机的**"。但数据库机按下电源后还要花半分钟生成世界地图——网页机这时候已经开机了，冲过去联机，发现对方还在读盘，直接崩溃。 加上 `service_healthy` 才是"**盯着数据库机的自检指示灯，等它变绿了再按网页机的电源**"。

### 4.7.4 ⚠️ 其它两处需要更新的旧写法

**① 删掉 `version:` 字段**

```yaml
version: '3.8'    # ❌ 已过时，删掉
services:
  ...
```

Compose 现在始终使用最新的 schema 来校验文件，这个字段仅供参考，写了还会收到"该属性已过时，将被忽略"的警告。**新项目直接从 `services:` 开头。**

**② `docker compose`（带空格），不是 `docker-compose`（带连字符）**

带连字符的是 Compose V1（Python 实现），已经停止维护。现在的 Compose V2 是 Docker CLI 的内置插件，用带空格的写法。功能和参数基本一致，但 V2 里项目名/容器名的分隔符从下划线改成了连字符（因为下划线在 DNS 主机名里不合法）。

**③ 文件名推荐用 `compose.yaml`**

Compose 支持 `compose.yaml`（官方推荐）、`compose.yml`、`docker-compose.yaml`、`docker-compose.yml`。新项目建议用 `compose.yaml`，老项目沿用 `docker-compose.yml` 也完全没问题。

### 4.7.5 💡 神奇的"内置局域网"：服务名即域名

Compose 会为这份配置里的所有容器**自动创建一个专属的内部网络**（就是 4.6 节讲的自定义 bridge），因此自带 DNS 解析。

在 `web` 服务的代码里连数据库，**不需要知道 MySQL 容器的 IP**，直接把主机名写成**服务名 `db`**：

```text
mysql://root:secret_password@db:3306/my_game_db
                             └┬┘ └─┬─┘
                          服务名  容器内原始端口（不是宿主机映射端口）
```

🎮 **比喻**：Compose 自动帮你拉好了局域网线并配好了通讯录。网页游戏机想找数据库游戏机，直接喊一声"db"，房间里的路由器就知道该把话传给谁。

### 4.7.6 💡 `docker run` vs `docker compose` 该用哪个？

||`docker run`|`docker compose`|
|---|---|---|
|适合|临时测试、跑单个孤立容器|多容器协作的正式项目|
|配置存在哪|一长串命令行参数，敲完就忘|一个 YAML 文件，**可进 Git 版本管理**|
|团队协作|靠口口相传和文档|`git clone` + `docker compose up -d` 就完事|

> 💡 **实用建议**：即使你只有**一个**容器，只要它的启动参数超过三四个，也建议写成 Compose 文件。 因为半年后你绝对记不起当初那串 `docker run` 加了哪些参数，但 YAML 文件永远在。

## 4.8 Docker Compose 日常运维命令清单

推荐统一使用官方规范语法 `docker compose`（中间带空格）。

### 一、服务生命周期管理

|命令|作用说明|🎮 比喻|
|---|---|---|
|`docker compose up -d`|依据配置文件在后台创建并启动所有服务|**总电源开机**：搬机器、插盘、组网、顺序通电|
|`docker compose up -d --build`|**代码或 Dockerfile 有改动时**，强制重新构建镜像再启动|**换盘开机**：重压带最新代码的新光盘再插上|
|`docker compose stop`|停止所有容器（不删除容器与网络）|**按关机键**：切断电源，设备保留在桌上|
|`docker compose start`|重新启动先前 stop 的容器|**重新开机**|
|`docker compose restart [服务名]`|重启全部或指定服务（配置改动后常用）|**按指定机器的 Reset 键**|
|`docker compose down`|停止并**删除**所有容器和网络（**具名卷保留**）|**清空台面**：拆走游戏机和网线，只留记忆卡|
|`docker compose down -v`|额外**删除具名卷**（⚠️ 数据一起没，慎用）|**彻底清场**：连记忆卡一起销毁|
|`docker compose pull`|只拉取最新镜像，不启动|**只去商店进货，先不开机**|

### 二、状态查询与日志排错（最高频）

|命令|作用说明|🎮 比喻|
|---|---|---|
|`docker compose ps`|查看本项目所有容器的状态与端口映射|**盘点联机台面**：哪台开着、各插了什么线|
|`docker compose logs -f [服务名]`|**排错第一命令**：实时追踪日志|**盯监控屏**：实时看某台机器的运行输出|
|`docker compose logs --tail 100 [服务名]`|只看最后 100 行，避免被历史日志刷屏|**只翻最近 100 条记录**|
|`docker compose top`|查看各容器内正在运行的进程|**查看每台机器内部跑了哪些任务**|
|`docker compose config`|校验 YAML 语法并输出解析后的最终配置|**验算配方总表**：看有没有写错、变量有没有漏填|

> 💡 `docker compose config` 是被严重低估的命令。它会把 `.env` 变量全部代入展开，**你能直接看到 Compose 最终"理解"成了什么样**，比对着 YAML 猜快得多。

### 三、容器交互与调试

|命令|作用说明|🎮 比喻|
|---|---|---|
|`docker compose exec <服务名> <命令>`|进入正在运行的服务容器内部执行命令|**拿起指定那台机器的手柄**|
|`docker compose run --rm <服务名> <命令>`|用相同配置起一个**一次性**容器执行任务，跑完自动删|**临时加开一台测试机**，用完即拆|

区别记忆：**`exec` 是钻进已经开着的机器；`run` 是另开一台新机器。** 数据库迁移、跑测试这类一次性任务用 `run --rm`；查日志、连数据库排错用 `exec`。

## 4.9 实战汇总速查表

|实战|核心命令|涉及概念|关键机制|🎮 比喻|
|---|---|---|---|---|
|**4.1 生命周期**|`docker run --name test1 alpine echo "hi"`<br>`docker run -d --name test2 alpine sleep 60`<br>`docker ps` / `docker ps -a`|主进程 (PID 1)<br>退出码|**容器寿命 = 主进程寿命**。主进程一退，容器立刻 `Exited`；只有主进程常驻，容器才 `Up`|**开关机**：播完台词立刻断电；跑倒计时则挂机 60 秒|
|**4.2 端口映射**|`docker run -d -p 127.0.0.1:8080:80 --name my-nginx nginx`|后台运行 `-d`<br>端口映射 `-p`|`-d` 后台静默；`-p 宿主机:容器` 把外部请求转发进隔离的容器|**拉网线专线**：把客厅 8080 插座接到游戏内 80 号门|
|**4.3 数据持久化**|`docker run -v mysql_data:/var/lib/mysql ...`（具名卷）<br>`docker run -v ~/conf:/etc/nginx/conf.d:ro ...`（绑定挂载）|具名卷 / 绑定挂载<br>`-v` `--mount`|数据脱离容器独立存在，容器删除后数据保留|**记忆卡 / U 盘**：砸了游戏机，存档依然完好|
|**4.4 环境变量**|`docker run -e MYSQL_ROOT_PASSWORD=... mysql:8.4`|环境变量 `-e`<br>`--env-file`|通用镜像无需重构，启动时注入参数完成个性化初始化|**开机初始化菜单**：插盘瞬间填入密码和城市名|
|**4.5 自定义镜像**|`docker build -t my-app:1.0 .`<br>`docker run -d -p 5000:5000 my-app:1.0`|构建上下文<br>分层缓存|读 Dockerfile 逐层构建，业务代码与运行环境固化成新镜像|**工厂压制专属光盘**|
|**4.6 容器网络**|`docker network create my-net`<br>`docker run --network my-net ...`|自定义 bridge<br>内置 DNS|**自定义网络才有容器名 DNS 解析**；容器互访走原始端口|**组联机房间**：机器之间直接喊名字就能找到对方|
|**4.7 Compose 编排**|`docker compose up -d`<br>`docker compose down`|服务编排<br>healthcheck|`services` 定义多容器，`depends_on + condition` 控制真正的就绪顺序，服务名即域名|**多机联机总表**：一键搬机器、插盘、组网、按顺序通电|

### 💡 六大核心铁律（速记）

1. **生命周期**：容器里没有前台常驻的主进程，容器必定"一闪而过"。
2. **网络隔离**：外部要访问容器服务，必须做端口映射；容器内服务必须监听 `0.0.0.0`。
3. **数据安全**：一切需要活过容器生命周期的数据（数据库/上传文件/日志），必须挂载出去。
4. **容器互访**：用自定义网络 + 服务名 + **原始端口**，绝不用 `localhost` 和宿主机映射端口。
5. **就绪 ≠ 启动**：`depends_on` 默认只管启动顺序，要等就绪必须配 `healthcheck` + `condition: service_healthy`。
6. **版本可复现**：镜像标签写死版本号，`latest` 只用于本地随手玩。

# 第五章：排错手册

> 学会排错，你才真正会用 Docker。这一章是全篇最实用的部分，建议加书签。

## 5.1 万能排错四步法

无论遇到什么问题，按这个顺序走，能解决 80% 的情况：

```
① docker ps -a          → 容器在跑吗？如果 Exited，退出码是几？
        ↓
② docker logs <容器>     → 它临死前说了什么？(报错几乎一定在最后几行)
        ↓
③ docker inspect <容器>  → 挂载路径、环境变量、网络配置是不是我以为的那样？
        ↓
④ docker exec -it <容器> sh → 进去亲眼看看：文件在不在？端口通不通？
```

🎮 **比喻**： ① 看电源灯亮不亮、断电时闪的错误码是几 → ② 调出黑匣子看断电前最后的画面 → ③ 拆开外壳核对接线图 → ④ 亲自钻进机器里摸一摸。

> ⚠️ 第 ④ 步的小陷阱：很多精简镜像（`alpine` 及基于它的镜像）**没有装 `bash`**，只有 `sh`。 `docker exec -it xxx bash` 会报 `executable file not found`（退出码 126/127）。改用 `sh` 即可。

## 5.2 常见报错速查表

|报错信息|含义|解决方案|
|---|---|---|
|`Bind for 0.0.0.0:8080 failed: port is already allocated`|宿主机 8080 端口已被占用|`docker ps` 找出占用的容器删掉；或换端口 `-p 8081:80`|
|`Cannot connect to the Docker daemon`|Docker 服务没启动|Mac/Win：打开 Docker Desktop；Linux：`sudo systemctl start docker`|
|`permission denied while trying to connect to the Docker daemon socket`|当前用户不在 docker 组|`sudo usermod -aG docker $USER`，然后**重新登录**|
|`exec format error`|**镜像的 CPU 架构和你的机器不匹配**|Apple 芯片 / ARM 服务器上跑只有 amd64 版本的镜像时常见。加 `--platform linux/amd64`（会走模拟，慢），或找 ARM 版镜像|
|`no such file or directory`（容器启动时）|启动命令指向的文件不存在|检查 `CMD`/`ENTRYPOINT` 路径、`WORKDIR` 是否正确、文件有没有真的被 `COPY` 进去|
|`standard_init_linux.go: exec user process caused "no such file or directory"`|脚本的换行符是 Windows 的 CRLF|把脚本转成 LF 换行；Git 用户配 `.gitattributes`|
|`Permission denied`（访问挂载目录时）|宿主机文件属主 UID 与容器内用户不匹配|`--user $(id -u):$(id -g)`，或调整宿主机目录属主。**别用 `chmod 777`**|
|`Exited (137)`|被 SIGKILL 强杀|**绝大多数是内存不足被 OOM Killer 干掉**。`docker stats` 看内存，加 `--memory` 限制或扩容|
|`Exited (1)` 且日志有 traceback|程序自身报错|看日志最后几行，是业务问题不是 Docker 问题|
|`toomanyrequests: You have reached your pull rate limit`|Docker Hub 拉取次数超限|`docker login` 登录账号提升额度；或配置镜像加速器/私有仓库|
|容器 `Up` 但浏览器打不开|① 服务监听了 `127.0.0.1` 而非 `0.0.0.0`<br>② 忘了 `-p`<br>③ 服务还在启动中|逐一排查。`docker logs` 确认服务真的起来了|
|改了代码但运行的还是旧版本|镜像没重建|`docker compose up -d --build`，或 `docker build` 后重新 run|

## 5.3 常用排错命令清单

```bash
# —— 查看与监控 ——
docker ps -a                              # 找出异常退出的容器和退出码
docker logs -f --tail 100 <容器>          # 看日志（-f 持续追踪，--tail 限制行数）
docker logs --since 10m <容器>            # 只看最近 10 分钟的日志
docker stats                              # 实时看 CPU / 内存 / 网络占用（排查 OOM）
docker inspect <容器>                     # 完整配置 JSON
docker inspect -f '{{.State.ExitCode}}' <容器>          # 只取退出码
docker inspect -f '{{json .Mounts}}' <容器>             # 只看挂载情况
docker port <容器>                        # 只看端口映射

# —— 进入容器排查 ——
docker exec -it <容器> bash               # 进入交互终端
docker exec -it <容器> sh                 # 镜像里没有 bash 时用这个
docker exec <容器> ls -la /app            # 不进去，直接执行单条命令
docker exec <容器> env                    # 看容器内实际的环境变量

# —— 容器启动就崩、根本进不去怎么办？——
# 覆盖启动命令，强行起一个只跑 shell 的容器，进去手动排查
docker run -it --rm --entrypoint sh my-broken-image:1.0

# —— 文件传输 ——
docker cp <容器>:/app/error.log ./        # 从容器里捞日志出来
docker cp ./fixed.conf <容器>:/etc/nginx/ # 把修好的配置塞进去（临时验证用）

# —— 强制清理 ——
docker rm -f <容器>                       # 强停并删除
docker rm -f $(docker ps -aq)             # ⚠️ 删除所有容器
```

> 💡 **最实用的一招**：容器一启动就崩、`exec` 都来不及进去时，用 `docker run -it --rm --entrypoint sh <镜像>` 覆盖掉启动命令，让容器只跑一个 shell。这样你就能进到"和崩溃现场完全一样的环境"里，手动一条条执行启动命令，看它到底卡在哪。 🎮 **比喻**：游戏一开机就闪退，那就用工程模式启动，跳过自动加载，让你能手动一步步试。

## 5.4 实战案例

### 案例一：修改了代码，但运行结果还是旧的

- **原因**：`docker compose up -d` 会优先复用本地已有的镜像，**不会自动重新构建**。
    
- **解法**：
    
    ```bash
    docker compose up -d --build
    ```
    
- **如果加了 `--build` 还是旧的**：多半是构建缓存的层没被正确判定为失效（比如你只改了没被 `COPY` 进去的文件）。强制不用缓存重建一次：
    
    ```bash
    docker compose build --no-cache && docker compose up -d
    ```
    

### 案例二：某个容器启动后立刻退出

```bash
# 1. 确认服务名和退出码
docker compose ps -a

# 2. 定位崩溃日志（报错一定在最后几行）
docker compose logs --tail 100 <崩溃的服务名>

# 3. 如果日志也是空的，说明它连启动都没启动起来，用工程模式进去看
docker compose run --rm --entrypoint sh <服务名>
```

常见原因：配置文件路径写错、必填环境变量没给、数据库密码不对、端口在容器内被另一个进程占用。

### 案例三：改了 `compose.yaml` 里的环境变量或端口，但没生效

- **原因**：`docker compose restart` **只是重启容器进程，不会重新读取 YAML 配置**。
    
- **解法**：直接再 `up` 一次。Compose 会自动比对配置差异，**只重建配置发生变化的那些容器**：
    
    ```bash
    docker compose up -d
    ```
    

🎮 **比喻**：`restart` 是按 Reset 键，机器还是照着旧的开机设置启动。`up` 才是重新照着新的配置总表检查一遍，发现哪台机器的接线跟表上不一样，就把那台重新搭一遍。

### 案例四：第一次 `up` 时 Web 服务崩溃，第二次就好了

- **原因**：见 4.7.3。`depends_on` 短语法只保证启动顺序，数据库还没初始化完 Web 就冲上去连了。
- **解法**：给数据库加 `healthcheck`，Web 的 `depends_on` 改用 `condition: service_healthy`。同时在应用里加重连重试逻辑。

### 案例五：磁盘被 Docker 吃满了

```bash
# 1. 先看清楚谁在占地方
docker system df           # 分类统计：镜像 / 容器 / 卷 / 构建缓存各占多少
docker system df -v        # 详细到每一个镜像和卷

# 2. 温和清理：删掉已停止的容器、悬空镜像（没有标签的中间层）、未使用的网络和构建缓存
docker system prune

# 3. 更彻底：额外删除所有「没有被任何容器使用」的镜像
docker system prune -a
```

> 🚨 **绝对不要无脑执行 `docker system prune -a --volumes`。** 加上 `--volumes` 会**连同所有未被使用的具名卷一起删除**。如果你的数据库容器此刻恰好是停止状态，它的数据卷就会被判定为"未使用"——**你的数据库数据会被永久删除，没有回收站，没有确认第二次**。 需要清卷时，请先 `docker volume ls` 逐个确认，再用 `docker volume rm <指定卷名>`。

🎮 **比喻**：`prune -a --volumes` 相当于对客厅喊一句"把所有没在用的东西全扔了"。清洁工看到那张记忆卡插在关机的游戏机上，判定"没在用"，连同你三年的存档一起进了垃圾车。

# 第六章：生产环境最佳实践

> 这一章的每一条，都对应着真实世界里发生过的事故。

## 6.1 安全

|实践|说明|
|---|---|
|**不要以 root 运行容器**|容器默认用户是 root。加 `USER appuser` 切换到普通用户，一旦应用被攻破，攻击面小得多|
|**密钥绝不写进镜像**|`COPY . .` 会把 `.env`、私钥永久烧进镜像层，后面 `rm` 也删不掉。用 `.dockerignore` 拦住它们|
|**环境变量不是保险箱**|`docker inspect` 能看到明文。真正的敏感信息用 Docker Secrets 或云厂商的密钥管理服务|
|**端口绑定到 `127.0.0.1`**|`-p 3306:3306` 会把数据库暴露到公网。加上 IP 前缀：`-p 127.0.0.1:3306:3306`|
|**镜像标签写死版本**|永远不用 `latest`。可复现性是安全的前提|
|**定期扫描镜像漏洞**|`docker scout cves <镜像>`，或用 Trivy 等工具接进 CI|
|**用官方镜像或可信来源**|Docker Hub 上任何人都能上传镜像，来路不明的镜像可能带挖矿程序|
|**只读根文件系统**|`--read-only` 让容器无法写入自身文件系统（配合 `--tmpfs` 提供临时目录），大幅提高安全性|

## 6.2 资源限制

容器默认**不限制**内存和 CPU。一个内存泄漏的容器足以把整台宿主机拖垮，所有服务陪葬。

```bash
docker run -d \
  --memory="512m" \        # 内存上限，超了会被 OOM Killer 干掉（退出码 137）
  --memory-swap="512m" \   # 内存+交换区上限，设成和 memory 一样即禁用 swap
  --cpus="1.5" \           # 最多用 1.5 个 CPU 核心
  my-app:1.0
```

Compose 里的写法：

```yaml
services:
  web:
    image: my-app:1.0
    deploy:
      resources:
        limits:
          cpus: '1.5'
          memory: 512M
```

🎮 **比喻**：给每台游戏机的电源装一个限流保险丝。某台机器发疯狂抽电时，只烧它自己的保险丝，不会拉闸让整个客厅停电。

## 6.3 日志管理

容器日志默认**无限增长**，几个月后能吃掉几十 GB 磁盘。在 `/etc/docker/daemon.json` 里配置全局轮转：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

意思是每个容器最多留 3 个 10MB 的日志文件，超了自动滚动删除。

**另一条原则**：容器内的应用应该**把日志直接打到标准输出（stdout/stderr）**，不要自己写日志文件。这样 `docker logs` 才能收集到，也才能接入统一的日志系统。

🎮 **比喻**：让游戏机把运行信息直接显示在屏幕上，而不是偷偷记在机器内部一个你看不见的小本子上——小本子会写满，而且机器一拆就没了。

## 6.4 镜像瘦身清单

|手段|效果|
|---|---|
|用 `-slim` 或 `-alpine` 变体基础镜像|通常能省几百 MB|
|**多阶段构建**（见 3.5）|编译型项目和前端项目能省 90% 以上|
|合并 `RUN` 并在同一层清理临时文件（见 3.1）|避免"删了却没变小"|
|`pip install --no-cache-dir` / `npm ci --omit=dev` / `apt-get clean`|清掉包管理器缓存|
|写好 `.dockerignore`|避免把 `.git`、`node_modules` 打进去|
|`docker history <镜像>` 定位大层|找出到底是哪一步把镜像撑大的|

> ⚠️ **关于 alpine 的一个提醒**：alpine 用的是 musl libc 而非 glibc，某些 Python 包（需要编译的科学计算库）在上面会安装极慢甚至失败。Python 项目通常 **`-slim` 比 `-alpine` 更稳妥**。

## 6.5 容器设计哲学

|原则|含义|🎮 比喻|
|---|---|---|
|**一个容器只跑一个主要进程**|别在一个容器里塞 Nginx + PHP + MySQL。拆成三个容器|一台游戏机专心跑一款游戏，别指望它同时当电视机和路由器|
|**容器应该是无状态的**|所有需要保留的状态放进卷或外部服务。容器本身随时可以被删除重建|游戏机是易耗品，存档在记忆卡上。机器坏了换一台就行|
|**配置从外部注入**|同一个镜像通过不同环境变量部署到开发/测试/生产|同一张光盘，靠开机菜单适配不同玩家|
|**不可变基础设施**|需要更新时，**重新构建镜像并替换容器**，而不是 `exec` 进去手改|要改游戏内容就重压一张新光盘，别拿螺丝刀撬开机器改硬盘|

最后这一条尤其重要。**你 `exec` 进容器手动改的任何东西，在容器重建时都会消失**，而且没有任何记录，下一个接手的人完全不知道你做了什么。所有改动都应该回到 Dockerfile 或配置文件里。

## 附录 D：下一步学什么

学完本笔记，你已经能独立把一个项目容器化并部署。接下来的路线：

1. **Dockerfile 进阶**：多阶段构建的高级用法、`BuildKit` 的 cache mount 和 secret mount、多架构镜像构建（`docker buildx`）。
2. **镜像仓库**：把镜像推到私有仓库（Harbor / 云厂商容器镜像服务），配合 CI 自动构建推送。
3. **CI/CD**：GitHub Actions / GitLab CI 里自动构建镜像并部署。
4. **Kubernetes (K8s)**：当你需要跨多台服务器管理几十上百个容器、需要自动扩缩容和故障自愈时，Compose 就不够了。 🎮 **比喻**：Compose 管的是**你客厅里这一桌**的联机。K8s 管的是**整个电竞馆几百台机器**的调度——哪台机器坏了自动换一台顶上，人多了自动多开几台。
5. **可观测性**：Prometheus + Grafana 监控容器指标，ELK / Loki 收集日志。
