# Vault Review

生成的是**草稿**，供用户编辑确认，不要自称"复盘已完成"。

## 步骤

1. **确定时间范围**：用户没指定就默认最近 7 天（自然周）。

2. **收集素材**：
   - `git log --since=<start> --until=<end> --name-status` 看这段时间新增/修改/重命名了哪些文件，重点关注 `Knowledge_Base/` 下的新增笔记和 `Daily-Task-List/YYYY/Month/` 下本期日期范围内的每日文件（`YYYY-MM-DD.md`）。
   - 读一下本期覆盖的每日文件，摘出标记完成或明显进展的条目。2026-08-01 之前的历史记录在 `Daily-Task-List/Archive/YYYY/N月任务清单.md`（旧版月度大文件），只在复盘范围跨到那之前时才需要看。
   - 如果 `Inbox/` 里有本期新增但还没归档的草稿，在复盘里提醒用户处理掉。

3. **按 `_templates/Review-Template.md` 的结构生成内容**：
   - 完成了什么：来自任务清单里的完成项。
   - 新增/更新的知识笔记：列出 git log 里新增的 `Knowledge_Base/` 笔记路径，每条配一句从笔记内容提炼的摘要（不要只贴文件名）。
   - 遇到的问题/待解决：从任务清单里没打勾、或者笔记里提到"待解决""TODO"之类的条目里找。
   - 下期计划：留空或给出基于本期未完成事项的建议，让用户自己填。

4. **写入文件**：路径为 `Daily-Task-List/Reviews/<year>/<YYYY>-W<周数>.md`（或整月复盘用 `<YYYY>-<MM>.md`），frontmatter 按模板补 `period_start`/`period_end`。

5. **回报**：告诉用户生成的文件路径，并提示这是草稿，建议过一遍再确认。

## 不要做的事

- 不要凭空编造"完成了什么"——只基于任务清单和 git log 里能找到依据的内容。
- 不要覆盖用户已经手写过的同名复盘文件，如果已存在就追加或另存为 `-draft` 后缀，并提醒用户。
